@AGENTS.md

`README.md` is detailed on setup, the API server, sessions, the Bluetooth printer and the path alias — read it rather than rediscovering that here. **Its "Project structure" tree is stale**: it still lists eight sections and `stores/` that were deleted (see "Where this repo actually is" below). ## Commands

- `npm start` — Metro dev server, then pick a platform.
- `npm run android` / `npm run ios` — **native builds** (`expo run:*`), not `expo start --platform`. The app needs a dev build: `react-native-bluetooth-classic`, `expo-secure-store`, `@expo/ui` and `lottie-react-native` are native modules, and in Expo Go the printer reports itself unavailable and sessions silently fall back to memory-only. **`@expo/ui` is the one that fails loudly**: every bottom sheet in the app is one of its native views, so a JS-only reload after it was added shows nothing but an "Unable to get view config" crash. Rebuild rather than reload after any change to the native dependency list.
- `npm run web` — `expo start --web`.
- `npm run lint` — `expo lint`. Baseline is **0 errors, 18 warnings**, all pre-existing `import/no-duplicates` and unused-var warnings inside `components/ui/*` (vendored gluestack). Treat any warning outside those files as yours.

  `eslint-config-expo` 57 turns two React Compiler rules into **errors**: `react-hooks/set-state-in-effect` and `react-hooks/refs`. They found thirteen real sites in code the upgrade did not touch, and how each was answered is worth knowing before adding a fourteenth:
  - **A pure fact does not need an effect.** A malformed `:id` in the URL is known when the params arrive, so the three detail screens derive their failure page during render instead of writing it from an effect.
  - **Loading is derivable too.** `app/produk/index.tsx` keeps "the key I want loaded" (built during render) and "the key I have loaded" (written once when a read settles); loading is the two disagreeing. Nothing is set on the way in, and a stale response cannot un-set a flag the next request just set. Copy this shape rather than a `setLoading(true)` at the top of a fetch effect.
  - **Adjusting state when a prop changes belongs in render**, not an effect — `components/shell/record-list.tsx` prunes its selection that way now, which also removed a frame where the selection bar counted a row that had already left the list.
  - **A stable value read during render is `useState(() => …)`, not `useRef(…).current`.** The ref form is what `react-hooks/refs` forbids, and for `new Animated.Value(1)` it also rebuilt the value on every render only to discard it.
  - **One site still carries a scoped `eslint-disable-next-line`, with the reason written above it.** It is a false positive, not a silenced bug: `app/penerimaan-susulan/baru.tsx`'s seeded-load effect calls a function whose every `setState` sits after an `await`, and the rule cannot see through that function boundary to tell. The pembelian section's own two — `setLoading(true)` at the head of a fetch effect, queued for this port — went when the section was ported (issue #24), on the same "key wanted vs. key loaded" shape `app/produk/index.tsx` established.
- `npx tsc --noEmit` — not a package script, but **the only real check on a repo with no tests**. Run it before claiming a change works. There is no test runner configured; do not invent one to satisfy a request.
- `npx expo export --platform android` — the closest thing to a build test. Current bundle is **~5.6 MB**; a sudden jump means a dependency got pulled in.
- `npx openapi-typescript contracts/openapi.yaml -o types/api.ts` — after any contract change.
- `npx expo prebuild --platform android` — after touching `app.json` plugins. A JS reload is not enough.

**Typed routes are generated by the dev server, not by `export`.** `app.json` sets `experiments.typedRoutes`, and `.expo/types/router.d.ts` is only rewritten when Metro boots. So after adding or deleting a route, `npx tsc --noEmit` fails on `Href` types until you start `npx expo start` once and let it regenerate — `expo export` alone will not do it, and the error reads like a bug in your code rather than a stale artifact.

`npm run reset-project` moves `app/` aside and leaves a blank one — it is a leftover from the `create-expo-app` starter. **Never run it.**

## Where this repo actually is

This matters more than anything else in this file, because the codebase is mid-rebuild and half of what a search turns up is scaffolding on its way out.

**The Ramah design system is the target, and it is the source of truth for what screens exist.** It lives in a Claude Design project (`63350d41-2bd9-499b-bd3f-b77d1a040c45`, "POS and stock management app"), read with the `DesignSync` MCP tool (`list_files` / `get_file`; auth via `/design-login`). Five files matter:

- `Panduan Gaya.dc.html` — the style guide, **currently revision 2**. It is the one that says *how* a screen is drawn, and it overrides the token files where the two disagree. Read it before porting anything; its rules are mirrored into `constants/theme-ramah.ts` (see "Styling").
- `Papan Layar.dc.html` — the flow map: seven flows, each screen a `dc-import` of the file below at a forced screen. Read this first for how screens connect, and for the navigation rules written at the foot of it.
- `LayarGudang.dc.html` — every back-office screen, as `sc-if` branches on one `screen` state: `login`, `konteks`, `home`, `katalog`, `produk`, `baru1`/`baru2`/`baru3`/`baruDone`, `ubah`, `minimum`, `pemasok`, `pembelian`, `doc`, `susulan`, `inbox`, `done`. **Its `endpoints` map (around line 1455) annotates which API call each screen is built on** — start there rather than guessing, but verify against the contract, because four of its claims do not hold (below).
- `LayarKasir.dc.html` — the POS screen, tablet three-column and phone two-section.
- `_ds/ramah-design-system-…/tokens/*.css` — palette, type scale, radii, spacing. The raw values, but **not the last word**: they size a consumer onboarding flow, and the style guide re-sizes several of them for merchant screens. Port from `constants/theme-ramah.ts`, which already reconciles the two — never by eye.

**The drawer is gone; `app/(admin)/_layout.tsx` is a tab navigator** (Beranda · Pendapatan · **Kasir** · Riwayat · Profil). It is **`expo-router/unstable-native-tabs`** — the real platform bar.

The board draws three roots — Beranda, Kasir, Nota — and the bar matched it until issue #24. **Katalog was never one of the three**: it moved to the root stack (`app/produk/`) the day the till took the middle slot, because "how much of this is left" is a question you arrive at rather than one you open the app on — Beranda already carries a Katalog tile and a reorder metric that push it, and the board draws that screen with a back arrow to home rather than as a root with no way back. The till is a place somebody stands for a whole shift, and it is a cashier's `homeRouteFor`. **The bar is hidden while Kasir is open** (`hidden` on `NativeTabs`, the container prop — it hides the *bar*, unlike `hidden` on a trigger, which makes a route unreachable), because the POS's bottom row is a 96pt pay button over a keypad and cannot share an edge with a tab bar. The way back out used to be the `more-vertical` menu the POS carries; issue #25 pared that menu down to "Kembali" and the till's own PPN setting once every other tab became reachable through the bar itself the moment Kembali is pressed.

**Nota (`pembelian`) was the third root, and issue #24 moved it beside the tabs too — `app/pembelian/`, same shape as Katalog.** Two things forced it, and either alone would have. First, a real bug: the docked "Faktur baru" pill sat under the tab bar rather than above it, because native tabs' automatic bottom inset — documented below — pads a tab's `ScrollView` reliably and a plain docked `View` sibling less so. Second, redundancy: Beranda's own "Pembelian" tile already opened `/pembelian`, so the tab was a second door to a screen already one tap from home — the same shape of problem the "Persetujuan" tile was in before that issue folded it into the "Diajukan" chip on this list. Moving the section to the root stack, where it pays its own insets exactly like `produk` and `pengaturan` do, fixed the inset and the redundancy in the same move. The bar held two roots after that: Beranda answers "what needs attention", Kasir is the place a cashier stands for a shift, and everything else — Katalog, Nota, Kiriman susulan, Pemasok, Laporan, Stok opname, Unit kerja — stayed a tap away from Beranda's grid.

**Issue #25 is what took the bar to five.** `Papan Layar.dc.html` always drew five — Beranda · Pendapatan · Kasir · Riwayat · Profil — and the two-root bar above was the state before that flow map's own bottom bar was actually built out. Kasir kept the middle slot: it is still the place somebody stands for a whole shift, and a phone's thumb reaches either edge from there. Pendapatan and Riwayat flank it because they are the two questions asked *about* the till — how much came in today, and what did it actually sell — read from `GET /laporan/laba-kotor` narrowed to one date and from `GET /penjualan` grouped by day, respectively (`app/(admin)/pendapatan.tsx`, `app/(admin)/riwayat.tsx`). Profil closes the row: it is where "ganti wewenang", "printer struk" and "keluar akun" live now, moved out of Kasir's `more-vertical` menu because that menu was their only home while the bar had nowhere else to send them. Katalog and Nota stayed off the bar — both are still questions you *arrive at* rather than ones you open the app to sit on, and both keep their door from Beranda's grid; adding either here on top of five would have meant six, past the five-tab ceiling both Android's Material bottom navigation and iOS's tab bar hold before an overflow starts eating the rest.

Riwayat's own rows push `app/penjualan/[id].tsx`, a section beside the tabs on the root stack — the same shape as `app/pembelian/`'s detail, and for the identical reason: every tab in `(admin)` mounts eagerly and keeps its own place in the navigator, so a detail pushed *inside* a tab lands on top of that tab's own history rather than returning to whichever tab the reader was actually on (see "Eager mounting also changes where back goes" below). `services/penjualan.ts` needed no changes at all for either screen — `listPenjualan`, `getPenjualan`, `AKSI` and `penjualanBus` already existed, wired up first for Kasir.

A first pass drew the bar by hand instead, on the argument that a native bar "cannot be told to look like" the Ramah spec. That was wrong, and it is recorded here so nobody re-derives it: `backgroundColor`, `tintColor`, `iconColor` and `labelStyle` cover the whole spec, and `VectorIcon` feeds a native tab item the same `@expo/vector-icons` Feather glyphs the rest of the app draws in. What the platform bar buys on top: real press feedback and haptics, the iOS 26 liquid-glass material and `minimizeBehavior`, tap-to-pop-to-root then tap-to-scroll-to-top, Android keyboard avoidance, and an accessibility tree a screen reader already understands.

`TAB_ITEMS` in `components/shell/AppShell.tsx` is the registry, not a convenience: with native tabs a route reaches the bar **only** through a `NativeTabs.Trigger`, so a directory added under `(admin)` cannot silently grow a fourth tab — and a directory there *without* a trigger is a route nothing can reach, which is why `produk` and `penerimaan-susulan` both sit on the root stack instead. Its one optional field is `ownsBottomInset`, which Kasir carries: Android wraps every tab screen in a `SafeAreaView` applying the bottom inset *for the tab bar*, and `disableAutomaticContentInsets` on the trigger switches that off for the one root that hides the bar and pads that edge itself.

**`penerimaan-susulan` lives on the root stack, not under `(admin)`.** Expo's docs are explicit that a trigger marked `hidden` "cannot be navigated to in any way" — not hidden-but-linkable — and `disabled` (SDK 56+) leaves a dead tab visible in the bar instead. Since the invoice screen pushes `/penerimaan-susulan/baru?idPembelian=` on every short delivery, the section had to move out. That is also where it belonged: a susulan is always started from the invoice that recorded the shortfall, and pushing it from the stack that *contains* the tabs means closing it returns to that invoice.

Two lineages are dead and must not come back: the drawer (a desktop pattern that hides the app's own map behind a gesture) and, before it, a `navShown` boolean over two absolutely positioned views with no swipe, no animation, and a menu that read `usePathname()` to know where it was.

**Eight sections were deleted on purpose**, because the new design does not draw them: `pelanggan`, `penjualan`, `retur-pembelian`, `mutasi-pemakaian`, `stok-opname`, `supplier`, `laporan`, `unit-kerja-ruang` — along with `stores/`, `hooks/use-local-store.ts` and their component folders. Two of those names came back since: `stok-opname` and `laporan` both got real sections of their own later (`app/stok-opname/`, `app/laporan/`), and `penjualan` got wired into Kasir and then, with issue #25, a screen of its own (`app/(admin)/riwayat.tsx` plus `app/penjualan/[id].tsx`). What survives under `app/(admin)/` today is the five tab roots — `beranda`, `pendapatan`, `kasir`, `riwayat`, `profil` — with `produk`, `pembelian` and `penerimaan-susulan` beside them on the root stack. **`pelanggan.ts`, `retur-pembelian.ts` and `supplier.ts` were kept the same way `penjualan.ts` was**, so those three currently have no screen: they are thin contract wrappers the rebuild will want back (the design's pemasok picker needs `supplier`). A service with no importer here is not dead code to tidy away.

**The whole `app/produk/` section is ported — it is the first section that is complete end to end, and it is the worked example for porting the next one.** Three screens and one dialog, each a board screen:

- `app/produk/index.tsx` — **Katalog produk** (C1), the reference for an *operational* list: grey canvas, white group cards, one docked green pill, everything imported from `constants/theme-ramah.ts` and `components/shell/ramah.tsx` rather than a `const D` block.
- `app/produk/[id]/index.tsx` — **Detail barang** (C2). The board's purpose for it is one line worth keeping in view: *menjelaskan kenapa saldonya segitu*. Two dense figure cards answer fast, the kartu stok answers completely. **Every figure on it belongs to one gudang**, which arrives as `?ruang=` from the catalogue so a row quoting "6 rim" opens a screen that also says 6 — `kartu_stok` partitions the balance chain per `(barang, ruang)` and `GET /product/{id}/kartu-stok` requires `id_ruang` for that reason. "Stok per gudang" is drawn **only** when more than one room holds the product, because with one it repeats the card above it word for word.
- `app/produk/baru.tsx` — **Produk baru** (G1 → G2 → G3 → `baruDone`), one route with four steps in state. `POST /product` takes the derived units in the same transaction, so the whole of G1 and G2 is one call that either creates everything or creates nothing; prices are one call per unit afterwards, because `harga-jual` needs an id that does not exist until the product does. A price that fails is **reported on the confirmation page**, not rolled back — the product is real by then.
- `app/produk/[id]/ubah.tsx` — **Ubah produk** (G4), a **route**, nested under the detail. It was a full-screen `Modal` on the dialog-vs-route rule below, and that rule was applied correctly to the wrong question: a `Modal` presents from the **bottom edge**, and every other push in the section slides in from the right, so the one form that changes a record announced itself as a different kind of thing from the two that create one. Being a route hands back the three things the dialog hand-rolled — the animation and the insets are the section's (declared once in `_layout.tsx`), and back returns to the detail because the detail is literally underneath it. It costs one `GET /product/{id}`, which is what buys a URL that works opened cold, and it answers over `produkDetailBus` instead of a callback prop. There is no `[id]/_layout.tsx`: with no layout of its own the folder flattens into the section's stack, which is what makes `router.dismiss()` pop straight onto the detail.

**`app/penerimaan-susulan/` is ported too**, and it is the worked example for a *document* section rather than a master one — the shapes here are what `pembelian` wants when its turn comes:

- `_layout.tsx` pays the section's three edges, for the same reason `produk`'s does. Both sections sit beside the tabs on the root stack, and `app/_layout.tsx` pays nothing.
- `index.tsx` — the list. **The board does not draw this screen at all**: `Papan Layar` runs F1 → F2 → F3 with no index anywhere, because a susulan is started from the invoice that recorded the shortfall. It exists because the documents have statuses and wait for somebody, and "which susulan are still in DIAJUKAN" is a question the board's flow cannot answer. Reached from Beranda's "Lihat semua" sheet. The row prints `atas PBL-…` rather than its own `PNS-…`: a shortfall is chased by the number written on the delivery note, not by one this document received after it was typed.
- `baru.tsx` — the creating half of F2. The invoice picker is a `RamahSheet` with a debounced `GET /pembelian?status=POSTED&statusPenerimaan=KURANG`, not an inline dropdown; on a phone the candidates want the whole width, and a dropdown covers the field it belongs to.
- `[id].tsx` — F2 at every status, and the buildable part of F3.
- `components/pembelian/turunan.tsx` — the line editor, now Ramah. Only susulan imports it (retur's screens were deleted, its `mode` kept). **The board's rule it exists to protect:** *"jumlahnya dibatasi sisa itu — batasnya ditulis di bawah tiap stepper, bukan baru muncul sebagai error."* The remainder is printed under every field before anything is typed and `+` stops at it; typing past it is still allowed and then said in red, because the invoice's remainder can be stale and a field that refuses to hold what somebody is reading off a delivery note is worse than one that disagrees out loud.

**Three things the board gets wrong about susulan, all resolved toward the contract.** Worth knowing before "fixing" the screens to match the drawing:

1. **Who posts.** The board's F2 carries one CTA, "Posting penerimaan", and its approval-inbox note says *"Penerimaan susulan diposting langsung oleh staf gudang."* The contract documents `/posting` as `DIAJUKAN → POSTED`, `Role: SUPERADMIN`, with `/ajukan` (`INVENTARIS` or `SUPERADMIN`) in between. Drawing it the board's way puts a button on the screen that the server answers 403 to, for the grant that does most of the typing. The four transitions stay.
2. **F3 "Selesai" is not buildable.** It names the new balance, and no response this flow has carries it — `PenerimaanSusulan` has quantities and values, not the resulting `stok_akhir`; getting it is one `GET /product/{id}/stok` per line. What survives is F3's *exit*: on a POSTED document every line row opens that product's kartu stok in the document's own ruang, which answers "kenapa saldonya jadi segini" with the whole chain instead of one number — and is a link per line, which is the honest shape for a document with several products.
3. **The destructive action is not a solid red button.** The board draws `Tolak nota` that way; guide §6 keeps red for "required and wrong" and allows one solid pill per surface, so `aksi-dialog.tsx` gives a `danger` transition red text on an outlined pill. Its explanation already says a rejection is a round trip rather than a deletion.

**`AKSI` is declared in flow order and that is not button order.** A supervisor on a `DIAJUKAN` document gets `[tolak, posting]` straight from the table, so the first control — and the green pill — would be *reject*. `app/penerimaan-susulan/[id].tsx` stably sorts the destructive ones to the end rather than reordering the table, which documents the flow and not one screen's dock.

**`components/shell/aksi-dialog.tsx` is Ramah, and every document group that writes `kartu_stok` shares it** — pembelian included, since issue #24 ported it. There is no version of it that is right for both palettes at once; a second copy is how the wording drifts apart again, which is the thing `shell/` exists to prevent. `DOKUMEN_RAMAH` in `components/shell/status-dokumen.ts` is the same four states toned for `RamahBadge`, **sharing the labels** with `DOKUMEN_META` rather than retyping them: a status is one word in this app and it has to be the same word on a ported screen and an unported one for as long as both exist. `BAYAR_META` and `TERIMA_META` (the payment and receipt states only pembelian's document group carries) got no such Ramah-toned counterpart on this port: the ported list and detail print both as plain caption text rather than a second badge beside the document's own — one filled badge is what a reader scans thirty rows for without reading any words, and a second competing for that glance would blunt it.

Two screens predate `constants/theme-ramah.ts` and still carry their own local palette blocks: `app/index.tsx` (login) and `app/pilih-peran.tsx` (konteks), the two consumer-shaped ones. `app/(admin)/beranda.tsx` is **Beranda** (B1/D1), and it is now the board's `home` branch drawn block for block: the flat `orange50` identity block, the konteks pill, one two-metric card with its update stamp, the stock-health score card, the eight-tile feature grid, and a three-row preview of the latest invoices — in that order, with nothing added and nothing reordered.

**Beranda is identical for every role — no branch on the grant anywhere in it.** The board draws B1 (gudang) and D1 (supervisor) as two screens while saying the layout deliberately does not change between them; this takes that to its conclusion. Guide §1 does permit a card to be hidden per role, and that permission is deliberately unused: two people at the same counter should see the same screen and be able to talk about it. A future card wanting otherwise has to argue for itself.

**Beranda is also where the difference between "drawn" and "answered" is worked out, and its file header is the record.** Three things the board draws are still not on it, each for a stated reason: the delta chip beside the first metric (guide §3 requires a delta to be relative to the same period, and no read here carries a previous one — a grey "0%" would be a claim, not a placeholder); a `--danger`-toned metric value (§3 puts tone in the chip, never in the number); and the bell's *contents* — the control is drawn, and pressing it opens a sheet that says there are no notifications, because there is no notifications endpoint and a control that is removed now has to be re-added later.

**The score card is drawn, and the number in it is derived rather than read.** No endpoint answers a stock-health score, so what the card shows is `100 × (1 − produk di bawah minimum ÷ produk aktif)` — the share of the active catalogue that is not below its reorder point, from two `total_item` counts the server did answer, stated in full on the card's accessibility label. That is a definition, not the invented "94 / 100" the layout-economy rule forbids, and it comes with two caveats written into the file header: the denominator counts every active product while the numerator can only hold products that have a `stok_minimum` set, and if either read fails the card is not drawn at all. `scoreTone()` still owns the three bands.

**All eight tiles are drawn, and four of them are disabled rather than absent.** Stok opname, pemasok, laporan and utang pemasok have no screens, so they render at 55% with a muted label — the board's own treatment for a tile that does not open — because the grid is also a map of what this app is going to be. Katalog, Pembelian, Unit kerja and Kasir go where they say. The Kasir tile is no longer the only route to the till — that is the middle tab now — and it stays anyway, because the grid is a map of what the app does and a feature missing from the map because it happens to be one tap away elsewhere is a feature somebody stops looking for. **Katalog's tile is the load-bearing one**: Katalog gave up its tab to the till, so this tile and the reorder metric above it are how that screen is reached. `FITUR` in that file is the single table the grid and the "Lihat semua" sheet both read — the guide caps the beranda at eight and puts the rest behind that button, so the cap is a `slice(0, 8)` and the sheet is the same list unsliced. Kiriman susulan is the ninth: it is normally started from the invoice that recorded the shortfall, so it does not spend one of the eight slots.

**Unit kerja replaced Persetujuan (issue #24).** Persetujuan opened `/pembelian` — the exact route the Pembelian tile beside it already opened, with no `status` filter ever actually sent, so two of the eight tiles led to one screen. The queue it promised is still one tap away as the "Diajukan" chip on that list; the freed slot went to `app/pengaturan/`, the unit kerja & ruang section issue #23 built and gave no tile at all, five dead-end screens being its only doors in until now.

**Every tile in the grid carries a 3D render, and four of the renders come from a second contributor.** Guide §8 restricts the grid to Iqonic Design's *Ulta Bizz* and *Bizzy Vol.2*, and neither draws stok opname, pemasok, unit kerja & ruang or a late delivery in the grid's own style — those four sit on renders from a second, IconScout-vetted pack instead (below). Unit kerja was the last tile on a Feather glyph, and it got off it by changing the question rather than hunting a gear: every `ruang` that section manages is a gudang, so the `warehouse` render is its subject. (The gears that do exist are the wrong language — Iqonic's free `Setting` is a glossy cyan cog from a third pack, *Bizzy Vol.2*'s cogs are purple and pink.) That render was Pemasok's, so Pemasok moved to the delivery van (`fast-delivery`) and Kiriman susulan off the van to `delivery-schedule`, a calendar beside a parcel — one concept per icon still holds. `LayarGudang.dc.html` draws all eight of its own tiles with a render and three of them are not Iqonic's, so the board had already spent that exception on Stok opname, Pemasok and Persetujuan; what was left was spending it well. Two of the board's three are unusable as drawn — `ai-analysis` and `ai-network` are a bar chart and a node graph and both carry a literal **"AI"** plate, which under a label reading "Stok opname" is worse than the line glyph it replaces. The third, `package-list`, is a clipboard with a parcel and a check and reads perfectly well on Persetujuan — it is simply not on this grid to read it, now that the tile is gone. The others were taken **from that same asset's pack** (Semusim Kreatif's ten-item logistics set, the one `package-list` itself belongs to), which is §8's rule applied rather than abandoned: the grid holds two coherent families, not three strangers. `assets/icons-3d/` holds ten renders — `shop`, `finance-report`, `edc-machine`, `growth-graph`, `deposit-box` from Ulta Bizz; `package-scale`, `fast-delivery` (the van), `warehouse`, `delivery-schedule` from the logistics pack, plus `package-list` itself, kept unreferenced rather than deleted because issue #24 explicitly leaves the persetujuan queue a real entry point to build later (`/pembelian?status=DIAJUKAN`) and that render already fits every one of the guide's rules for it. The reasoning is written out at `ART` in `app/(admin)/beranda.tsx`; read it before adding a tenth.

Read that header before adding anything to Beranda.

One rule the guide states flatly and is easy to break by good intentions: **a metric's value is always `--text-title`, never toned.** Tone belongs to the delta chip beside it. An early Beranda painted the reorder count orange, which read as an alarm the bare number does not justify — seven items below minimum is unremarkable in a shop stocking four hundred. Urgency lives in the score card underneath, whose tint band *is* the tone, and past that in Katalog's own reorder group. `app/(admin)/kasir.tsx` is on the Ramah palette now too, and is a mock only in its data.

`components/shell/ramah.tsx` is the Ramah counterpart of `components/shell/ui.tsx` — header, search field, chip (with an optional leading icon), section heading (with the design system's optional right-hand `action` word), the shortcut tile, the score card, the stacked list row, the bottom sheet, the flat error line, and all three buttons the system defines: `RamahPrimaryButton` (the one solid pill, whose `height`/`fontSize` exist for the till's 96pt pay button and nothing else), `RamahSecondaryButton` (outlined brand) and `RamahTertiaryButton` (outlined grey escape hatch). `RamahIconButton` carries the design system's four looks — `plain` for the back office, and `outline` / `tint` / `solid` which only the till uses, `solid` being how a mode that is currently *on* says so across a counter.

**It is also where the app's three animations live (issue #39), and three is the whole inventory — one per *state*, not one per screen.** `RamahAnim` is the table (`assets/lottie/`, all three pure vector, ~235 KB together, which is the whole of the bundle's 5.6 → 5.8 MB move); `RamahLottie` is the only thing that renders one, so no screen imports `LottieView` itself. What they are on: a search that matched nothing (`RamahEmptySearch`), the forward arrow on a positive action (`arrow` on `RamahPrimaryButton`), and the OCR wait in `components/pembelian/ocr-baca.tsx`. Four rules that are easy to break:

- **A search that found nothing and a list that has nothing are not the same state**, and only the first gets the illustration. Every caller keeps the `searching ? <RamahEmptySearch/> : <plain text>` branch — an empty catalogue has not failed to find anything, and "tidak ditemukan" over it misstates why the screen is blank.
- **`RamahEmptySearch` goes on a *screen*, never in a sheet.** A sheet is small, its options are the point, and its search field is still visible above the message; the pickers that live in one (`RamahSearchSheet`, the satuan pickers) keep their line of text. The till is the one screen on the small size (88), because its catalogue column has a cart and a keypad to share with.
- **`arrow` is a promise, not decoration.** It means *there is a screen after this one*: right on "Lanjut", wrong on "Simpan", "Posting" and the "Selesai" that closes a flow. It plays **once on press** rather than looping — a pill that animates forever is the only moving thing on a screen somebody reads standing in a storeroom. Three call sites used to pass `icon="arrow-right"`, which drew the arrow *before* the label it was meant to follow; `arrow` is that fixed.
- **The OCR wait is the only spinner worth replacing.** It runs for tens of seconds and its copy asks somebody to stand still; every other wait here is a page of a list or a `RefreshControl` and is over in under a second.

**`lottie-react-native` needs a second package for web, and npm will not install it for you.** Its `index.web.js` hard-`require`s `@lottiefiles/dotlottie-react`, which its `package.json` marks as an **optional** peer — so `npx expo install lottie-react-native` leaves it out, native keeps working, and the first `npm run web` after that dies on "Unable to resolve module @lottiefiles/dotlottie-react". Both are in `package.json` now. It is a web-only dependency: nothing in the native bundle reaches it, and adding it needs no rebuild.

(While confirming that, note `npx expo export --platform web` fails on something unrelated: static rendering runs the app in Node with `__DEV__` false, which trips `services/api.ts:29`'s release-build https guard against the `http://` URL in `.env.local`. `npm run web` is a dev server and does not. The android export only bundles, never executes, so it never sees it either.)

`hooks/use-reduce-motion.ts` is the accessibility switch, and the **fallback belongs to the surface** because what the motion was saying differs at each: a still frame of the same drawing for an empty search (`RamahAnim.still` — *not* `progress={0}`, both looping assets build themselves up over their first second and frame 0 is a blank square), a static Feather `arrow-right-circle` for the pill, and the `ActivityIndicator` it replaced for the OCR wait, because a still picture cannot say "still working".

The form and card shapes the produk port added, all of them the guide's own and all of them wanted by the next section too:

- **`RamahField`** is the guide's inverted field: a Caption label (12/16 Demi, grey) above a Title Small value (20/24 Bold), on a 1px underline (1.5px `borderFocus` when focused, **no glow** — a shadow marks a surface that floats, and a field is part of the page). Required is a red asterisk after the label, never the word "(wajib)". `prefix` is the "Rp" *inside* the line, because it is part of the value rather than a question about it. The point of the inversion is what a filled form then looks like: a summary. A boxed field weighs every row the same whether it holds anything or not.
- **`RamahPickerField`** is the same line when the value is chosen rather than typed, with a chevron and no caret. It exists because the board draws satuan dasar as a free-text box and the contract cannot take one — `POST /product` wants `id_satuan_dasar`, a foreign key into the `satuan` master, and an unknown id answers 400.
- **`RamahStackCard`** is the design system's `StackList`: the white card, with the hairline inserted *by the container* rather than by each row. Only the container knows which row is last, and the divider has to be inset by the card's own padding or it cuts the card in half. **Do not use it for an appending list** — it wraps its children, which means holding every row in one element and giving up windowing; `app/produk/index.tsx` flattens rows with their headings and lets each draw the edge it owns, and says so at its `Entry` type.
- **`RamahSteps`** is "Langkah 2 dari 3 · Satuan" over N 4px bars. No percentage and no ring: a three-step form needs to say which question is on screen, not that it is 67% finished.
- **`RamahSummaryCard`** is the `grey50` recap block — label left, value right. Deliberately the same component before saving (G3's foot) and after (`baruDone`), because what you were shown before is what you should be shown after.
- **`RamahStatCard`** is one of a pair of dense figure cards. **`tone` tints the card, never the figure** — guide §3, and this is the case it was written for: a balance under its reorder point is worth marking, and marking it by painting the number orange reads as an alarm a bare count does not justify. What turns orange is the note underneath. `note` is optional and is left off rather than filled with something that only restates a value already on screen next to it — a card whose note would just repeat a chip or heading above it (issue #27's "Di {gudang}" beside a gudang chip) gets no note at all.
- **`RamahNote`** is the grey aside for the one thing that actually blocks the reader right now — a gudang frozen by an open opname, a field locked against editing. It is not a place to teach the contract, the server, or a role's reasoning: no "kontrak tidak menulis…", no "yang dikirim ke server adalah…", no "dibaca oleh yang memverifikasi…", and never more than one fact. **One short sentence, roughly six words, or it does not survive.** If the fact does not change what the reader does next, delete the note rather than shorten it — issue #27 is the record of a whole pass of these that were explaining instead of blocking, and the same restraint applies to `helper=` on `RamahField` and to any other caption-sized aside. A hint's job is to sit quietly under a label; it must never out-weigh or out-explain the label and value above it.
- **`RamahBadge`** is a status pill in the five tones `LayarGudang.dc.html`'s `STATUS_META` defines, and the split between them is not decorative: `success` and `danger` are **filled**, the other three tinted. A filled pill is a document that has moved something it cannot take back, and the two filled colours are what somebody scanning thirty rows reads without reading any words. Take the label and tone from `DOKUMEN_RAMAH`, never per screen.

It and `ui.tsx` never meet in one screen: `ui.tsx` is gluestack over `theme-erp`, and a screen still rendering it is a screen the rebuild has not reached.

## The contract is the source of truth

`contracts/openapi.yaml` describes a backend this repo does not own, and `types/api.ts` is generated from it. **Check the contract before designing anything that depends on a filter, a sort, or a field.** Several plausible-sounding features are not buildable, and the gaps are not obvious from the screens:

- `GET /product` accepts only `page`, `size`, `search`, `is_aktif`. No sort parameter, and the list payload carries **no stock, no satuan and no harga** — those keys are absent, not empty. Fetching them per row is the N+1 the contract explicitly warns against.
- `GET /pos/product` is the one read that answers product + satuan + harga + `stok_akhir` for a whole page in three queries. It requires `id_ruang`, returns active products only, never carries HPP, and sorts an exact `kode_barang` match to the top — which is what a barcode scan needs. **This, not `GET /product`, is what the design's Katalog screen actually describes**, even though its endpoint note names the other path.
- There is no `DELETE /product`. The only removal is `PATCH { is_aktif: false }`, which is why archiving is treated as reversible everywhere.
- "Low stock" is a **separate endpoint**, `GET /product/stok-minimum`, pre-sorted worst-first — not a filter on the product list. It takes `page`, `size`, `id_ruang` **and `search`** (the search was added to the contract on this branch; regenerate `types/api.ts` if it is missing there). Its threshold is `total_stok <= stok_minimum`, and `stok_minimum = 0` never appears at all — zero is the column default, meaning "not set" rather than "may run out". Membership in this list is therefore the *whole definition* of "di bawah minimum", which is how Katalog groups rows by stock health despite `PosProduct` carrying no `stok_minimum`: `GET /pos/product` supplies every row, this endpoint supplies the ids, and both reads are narrowed to the same `id_ruang` so the two are comparing the same stock.
- `GET /product/{id}/kartu-stok` is the ledger behind a balance, and it breaks three of this API's own habits. `id_ruang` is **required** (the chain is partitioned per `(barang, ruang)`, so a history mixing rooms prints a running balance that never existed on one shelf). It sorts **ascending by `id`** — not by date, and not descending like every other list — because the chain is built in id order by the trigger while a reversal is stamped `time.Now()`, so date order can differ from the real order; a ledger is read top to bottom and the screen must not re-sort it. And a **reversal is identified by `id_kartu_stok_asal` alone** — `jenis_transaksi` is shared between a posting and the line that undoes it, so reading the kind off that field draws a cancellation as the movement it cancelled. Ascending order also means page 1 is the *oldest* twenty: `app/produk/[id]/index.tsx` reads page 1 for `total_page`, then the last page, and walks backwards from there.
- `POST /product` takes its derived `satuan` **in the same transaction** (up to 32), and registers the base unit automatically with `faktor = 1` from `id_satuan_dasar`. Prefer it over one `POST /product/{id}/satuan` per unit: a product that exists with two of its three units registered is a half-finished record somebody has to notice. There is **no `DELETE /product/{id}/satuan`**, and there should not be — a `faktor` is what every quantity already in `kartu_stok` was converted by — so a unit can be added and its factor corrected, never withdrawn. `app/produk/baru.tsx` offers a bin on a unit only while the product does not exist yet.
- Changing a price is `POST harga-jual` (a new version, closing the open one at the same date, so yesterday's sales keep yesterday's price); `PATCH` corrects an amount in place and answers 409 once a nota references it. `app/produk/[id]/ubah.tsx` picks between them by one test: a version that already starts **today** is corrected, everything else opens a new version — opening a second version starting today would ask `product_harga_jual_no_overlap` for a zero-length range.
- Two things the board says about products that the contract contradicts, and the contract wins. The board's G1 note claims **`kode_barang` is generated by the server** ("ditampilkan sebagai kabar, bukan isian") while its own drawing draws an input — it is **required** on `POST /product` and a duplicate answers 409. And the board draws a **barcode-scan button** beside that field, which nothing in this project can honour: there is no `expo-camera` and no barcode module in `package.json`, so the button is absent rather than dead. A scanner added later feeds the same field — `GET /pos/product` already sorts an exact `kode_barang` match to the top.
- **Kode barang is the one code a person types.** Every other `kode` in the contract — `unit-kerja`, `ruang`, `supplier`, `pelanggan` — is `nullable` and, as of issue #27, is never sent by this app: `components/pemasok/form.tsx`, `components/pengaturan/unit-kerja-form.tsx` and `components/pengaturan/ruang-form.tsx` have no `kode` field, in either their create or their edit route, and their `*Body()` helpers omit the key entirely rather than sending `null`. The backend does not yet generate one on create, so a record made through this app still shows "Tanpa kode" on its detail — that fallback stays until the contract's create endpoints are changed to fill it in. Do not re-add a typed `kode` field to any of those three forms; if a screen needs one, the fix is the backend generating it, not the form asking for it back.
- Paging is offset-based (`page`/`size`) with no cursor anywhere, so appending pages must de-duplicate by id.
- Money crosses the wire as **decimal strings**, never numbers. `services/decimal.ts` is the only place that boundary is crossed, in both directions.

**Three things the new design needs that the contract cannot serve.** Say so rather than faking them client-side:

1. There is no sort parameter anywhere — not on `GET /product`, not on `GET /pos/product`. The board's "Urut nama" chip has nothing behind it, and sorting an appended list client-side reorders only the pages already in hand, which is the same lie a client-side search over a paged list tells. Katalog ships without that chip.
2. There is no price tier. `product_harga_jual_no_overlap` guarantees exactly **one active price per (product, satuan) per date**, so the kasir board's "Umum / Langganan" chip has nothing behind it (the board fakes it with a hardcoded 7%).
3. No endpoint *produces* a PDF — `/dokumen` only accepts an uploaded invoice photo, and `laporan` answers JSON. A printed nota has to be rendered on the client or wait for a `GET /pembelian/{id}/cetak`. (The board's "PPN 11%" line is no longer on this list: `POST /penjualan` gained a `ppn` field on this branch. It is a **rupiah amount, not a rate** — the client computes 11% and sends the money, exclusive of the price, mirroring `pembelian.ppn` — so `total = subtotal - diskon_nota + ppn + pembulatan`.)

**Tutup buku (`/periode`, issue #12) is the one module every posting depends on without importing it.** Closing a month makes the trigger refuse any `kartu_stok` row dated inside it, from every module. Three things to keep: a month with **no row is open** (`GET /periode` lists closings, not a calendar — `app/periode/index.tsx` draws twelve months and fills in the rows it got); both `tutup` and `buka` are `SUPERADMIN` (`WriteArea` `periode`); and the server names the month in the 400 ("periode 2026-07 sudah TUTUP"), which `periodeTertutup()` in `services/periode.ts` parses so `AksiDialog` can link straight to that month. That link is the point of the module — without it a closed month fails postings with nothing in the app able to say why. An unrecognised message returns `null` and the error shows as it came.

## Auth, session, and permissions

Three layers that only make sense together:

1. `services/session.ts` holds the one signed-in session. A session has a token **and** an `active` context (the chosen grant). `hasActiveContext()` narrows to `ActiveSession`; `hasChosenContext()` is the stricter one the router uses.
2. **Routing is guarded by `Stack.Protected` in `app/_layout.tsx`, not by redirects in screens.** Three states, because this contract has one more than the usual pair: signed out (`index`), signed in with no grant picked (`pilih-peran`), and signed in with a **chosen active context** (`(admin)` and `kasir`). A guarded-off route is not in the navigator at all, so a deep link cannot reach it, and losing the session unmounts whatever is open. Do not reintroduce a `useRequireSession`-style hook: redirecting from an effect means mounting, fetching against a dead session, and painting a frame first.
   The guard is `hasChosenContext`, not `hasActiveContext` — a login with exactly one usable grant comes back with that grant **already active**, and `/pilih-peran` is still shown so the holder sees which role and unit kerja they are about to work as. `Session.contextChosen` is what tells "I picked this" from "this is all there was"; it is in-memory only, so a token refresh and a cold start do not re-ask.
   `index` is deliberately unguarded: it is the anchor every closing guard falls back to, and the one place that knows a cashier's home is `/kasir` and everyone else's is `/produk` (`homeRouteFor` — this is the value the tab rebuild will change). It answers with `<Redirect>`, not a `router.replace` in an effect. **Nothing signs out by navigating** — `logout()` drops the session and the guards do the rest.
3. `services/permissions.ts` — `useCanWrite(area)` / `useActiveRole()`. Roles are exactly `SUPERADMIN | INVENTARIS | CASHIER`; writes are split by **who owns the data**, not seniority. There is no `ADMIN` or `STAFF` in the contract.

`services/client.ts` **single-flights token renewal** (one `inFlight` promise) because refresh tokens are rotated and deleted on first use — two concurrent requests must not spend the same one. Do not add a second refresh path.

`services/permissions.ts` stops at the *entry* permission for a screen. Documents split further along the flow, because posting appends to an append-only `kartu_stok` and can only be reversed, never corrected — so it wants a second person. `services/alur-dokumen.ts` holds the vocabulary (`StatusAlur`, `AksiKey`, `AksiDokumen`, `pilihAksi`), and each document module holds **its own `AKSI` table**: one row per transition, with the status it starts from and the roles the server accepts.

**Where the second person stands is not the same in every group, and that is the thing to check first.** `pembelian` and `penerimaan-susulan` run four transitions: `INVENTARIS` types and submits, `SUPERADMIN` posts, rejects and cancels. `penjualan` runs **two** — `DRAFT → POSTED → BATAL`, with no `ajukan` and no `tolak` endpoint at all — because a cashier cannot make a buyer at the counter wait; there `CASHIER` types *and* posts, and `SUPERADMIN` holds the only undo, `batal`.

The tables stay per module even where the transitions match, because the sentence each one shows before an irreversible write is the point: posting an invoice values stock at the invoice, posting a susulan copies the harga pokok the invoice already fixed, posting a nota charges stock out at the moving average *and* is the one place `plafon_kredit` is enforced. `components/shell/aksi-dialog.tsx` is shared by all of them and knows nothing about which document it is confirming — every word, including whether a reason is collected at all, comes off the `AksiDokumen` it is handed. `components/shell/status-dokumen.ts` holds the badge maps (`DOKUMEN_META`, `BAYAR_META`); what stays under a section is what only that document can be, like `components/pembelian/status.ts`'s `TERIMA_META`.

## Screen architecture

- **A detail view or a create form is a route, not a `view` branch.** Push it (`router.push({ pathname: '/produk/[id]', params: { id } })`) and let the stack return. Every branch faked with `useState` was an Android back button that exited the section instead of going back, a record with no URL to deep link, and a scroll position restored by hand.
- **Section layout: `<section>/_layout.tsx` + `index.tsx` + `[id].tsx` + `baru.tsx`.** The `_layout.tsx` is a `Stack` with `headerShown: false`, `export const unstable_settings = { anchor: 'index' }`, and all three routes declared as `<Stack.Screen>` rather than left to the file tree, each carrying a `title` (nothing draws it; it names the route to the web document title and to accessibility). **The anchor is not optional** — without it a cold deep link to `/produk/12` builds a stack with nothing underneath, and `router.back()` leaves the app.
- Editing stays a **dialog on the detail** (the record is already on screen); the list's "Ubah" action pushes `[id]` with `?ubah=1`. Creating is the `baru` route. The dialog is `ModalShell` in `components/shell/ui.tsx` or, on a ported screen, a plain `Modal` drawn with `RamahHeader` — the split Expo documents: a dialog decided about the record already on screen is not a place in the app and wants no URL, while a flow with steps to link into is a route.

  **The board cannot tell you which side of that split something is on**, and the produk port is where that was worked out — including where the rule itself needed a second half. `LayarGudang.dc.html` is a flat state machine, so *everything* in it is a `screen`, G4 "Ubah produk" included. G4 was read as a dialog on the rule above (only reached from C2, returns to C2, about the record C2 is already showing) and shipped as a full-screen `Modal`. **That was wrong, and the reason is the second half of the rule: how a thing arrives is part of what it says it is.** A `Modal` presents from the bottom edge; a `Stack` push comes in from the right. Same section, same kind of work, two different animations — and the one that rises from the bottom reads as a sheet somebody is about to flick away, not a screen with six fields and a save. So the test is not only "is this a place in the app", it is also **"does it move like its neighbours"**; a form that fails the second is a route even when it passes the first. G4 is `app/produk/[id]/ubah.tsx` now. G1–G3 were always a route, because they are a flow with steps. What is never the test is how the board drew it.

  **One route with steps in state costs the Android back gesture**, and `app/produk/baru.tsx` pays it rather than fighting it: back leaves the whole flow, not one step. Nothing intercepts it and nothing should — `app.json` turns on the predictive back gesture, so Android begins animating the screen away before JS gets a say. The header arrow is what walks back a step; the system gesture means "I am done with this". Four routes would have fixed that and would have needed a draft store shared between them, which is the thing `stores/` was deleted for.
- **A query parameter read once into a ref only works on a pushed route.** `[id]`'s `?ubah=1` is safe because that screen is mounted fresh each time. A *section root* is kept mounted by its navigator, so a parameter aimed at one must be applied on arrival and then cleared off the URL (`router.setParams({ x: undefined })`) — otherwise the second visit carries the same value, the ref never re-reads, and nothing happens.
- Every detail and form has `goBack()` = `router.canDismiss() ? dismiss() : replace('/<section>')`. **`dismiss()`, never `back()`** — `dismiss` targets the closest `Stack`, the section's own; `back()` is offered to the outer navigator first, which may answer by switching sections instead of popping the screen. The `replace` covers a deep link with nothing to pop at all.
- A detail reached cold must render a **failure page**, not toast over a list that may not be behind it.
- **A detail's standing actions go in `headerRight`, as icons** (`IconAction` in `ui.tsx`, Feather via `@expo/vector-icons`), because they are the same two on every record of a section — edit, and archive — which makes them chrome, not content. Archive is `trash-2` in the danger colour and flips to `rotate-ccw` on an archived record: the contract has no `DELETE`, so the bin means "out of the way", and the way back is the same button pointing the other way. Every icon carries an `accessibilityLabel`. What does **not** become an icon is a one-off action whose label is the whole point — role-filtered transitions like Ajukan / Posting / Tolak read differently to each grant and stay text buttons in the body.
- Cross-route state has one shape: `hooks/use-record-bus.ts` carries writes from a detail back to the list still mounted underneath it (`saved` patches one row, `reload` re-reads page one). Each API-backed module declares its bus next to its row type (`produkBus`, `pembelianBus`, `susulanBus`, …). It is not a query cache and should not grow into one. `reloadAllRecords()` is what a context switch calls, because a grant carries a unit kerja and that invalidates every list at once.
- `components/shell/record-list.tsx` is the list. **A row does two things: tap opens the record, long-press starts multi-select.** No ⋮ menu and no swipe drawer — a row is a summary, and what you can do to a record lives on the record. Its chrome comes from the same file (`ListHeader`, `ListSearch`, `NewRecordRow`), not from each screen's `StyleSheet`. A row carries one badge, and `badgeTone` is what makes it a *status* rather than a label — a document's position in its flow is what the eye scans thirty rows for. If a list ever needs a fixed-column table again, the reason has to be written down first: columns want 640–880pt and a phone in portrait has ~354.
- Lists append rather than page: `PAGE_SIZE` 20, `onEndReached` guarded by an in-flight flag (it fires repeatedly — the threshold is not a guard), and a failed page halts the loop behind a "Coba lagi" button rather than a spinner that never ends. `app/produk/index.tsx` is the reference. Nothing saves a scroll offset: the list stays mounted under the pushed detail and keeps its own.
**`app/(admin)/kasir.tsx` is wired to the API now** — `GET /pos/product` for the catalogue (paged, appended, server-side search, and the scanner leans on its exact-`kode_barang`-to-the-top sort), `GET /ruang` for which gudang it sells out of, and **two calls to finish a sale**: `POST /penjualan` writes a `DRAFT`, `POST /penjualan/{id}/posting` moves the stock. Those two are the thing to understand before touching it. If the create succeeds and the posting fails the document *exists*, so the screen holds `draftId` and a second press posts that draft rather than writing another one — a dropped connection must not become two sales. The nota number is the server's (`nomor`, issued at creation, reset monthly by the document's own `tanggal`), so the header reads "Nota baru" until there is one; the board's invented "TRX-2609-018" is gone. **QRIS posts as `TUNAI`**: the contract's `jenis_pembayaran` answers *is the shop still owed money*, not which instrument the money came by, and a QRIS transfer has settled before the buyer leaves — the receipt still prints QRIS, which is a third value `ReceiptData.jenis` now carries. Still absent because the contract cannot serve them from a till: a price tier, a pelanggan (and so KREDIT), and diskon.

**PPN is a setting on that screen, not a constant.** It can be switched off entirely and its rate changed, from the `more-vertical` menu, remembered per device in `AsyncStorage` under `kasir.ppn`. Two reasons it is not a number in the file: plenty of counters do not collect output VAT, and the national rate has moved inside the working life of these shops. What crosses the wire is **rupiah, never the rate** — `penjualan.ppn` is money, mirroring `pembelian.ppn` — and it is exclusive, so `total = subtotal + ppn`. The totals row is drawn only when the tax is actually charged, and carries the rate in its label so the screen and the paper can never disagree about which one was applied.

- `app/(admin)/kasir.tsx` is **`LayarKasir.dc.html`, both layouts**, and it is the middle tab with the bar hidden, and it is on `theme-ramah` now — the blue `const K` block, the landscape lock, the pelanggan/kredit flow, the PIN gate, the F-key strip, diskon-nota, pembulatan and the history overlay are all gone, because the new board draws none of them. It is wired to the API — see the `GET /pos/product` / two-call-posting paragraph above this list.
  - **The layout is chosen at `large` (905pt), not at `tablet` (600).** The board's three columns are 352 + flexible + 392 inside a 1194pt frame; below ~900 the middle column has nothing left to be, so everything narrower gets the phone layout — a list with the cart docked under it and the keypad as a `RamahSheet`. The columns are flex ratios rather than fixed pixels so a 1024 and a 1366 tablet get the same proportions.
  - **Removing the lock is the point of having a phone layout**, so nothing here imports `expo-screen-orientation` any more.
  - **The "Umum / Langganan" chips are not drawn.** The board fakes the second tier with a hardcoded 7%, and the contract has exactly one active price per (product, satuan) per date. Same reasoning that dropped Katalog's "Urut nama" chip. **PPN is drawn**, because it is real now: 11% of the subtotal as a rupiah amount, on screen and on the receipt (`ReceiptData.ppn`, printed only when non-zero).
  - **One `more-vertical` button is the only chrome added to the board, and it carries two or three entries now, not four — issue #25.** "Ganti wewenang", "printer struk" and "keluar akun" moved to Profil, the fifth tab, because none of the three is about the till and every tab is a thumb's reach away once "Kembali" un-hides the bar. What is left: "Kembali" (the way out — with the bar hidden it is the only one, and it has to be), "Gudang" (only when there is a second one to pick), and PPN, a per-device setting this screen alone owns. `keluarKasir` asks `homeRouteFor` rather than hardcoding `/beranda`, and `replace`s rather than `back()`s: this is a tab root, so there is usually nothing to pop.
  - **It owns its bottom edge and nothing else.** Top, left and right are spent by the group layout outside the navigator; the bottom is this screen's because the bar it would be padding for is hidden. Spent three times, each by whatever owns that edge: the cart's totals foot, the keypad's CTA foot, and the product list's `contentContainerStyle` on the tablet.
  - It shadows RN's `Text` with a wrapper applying a size-derived `maxFontSizeMultiplier`, because dense POS chrome cannot absorb a blanket 1.4× cap — the cap goes *down* as the text gets bigger. Keep using that local `Text`.
- **The active role is permanent chrome, and switching does not go through logout.** `components/shell/role-switcher.tsx` exports `RoleChip` and `RoleSwitcherSheet` (it is `StyleSheet` + `constants/theme-erp` rather than NativeWind precisely so kasir, which has its own palette, can use the same one). The chip is a label, not a button, for the majority who hold one grant. A switch issues a **new token** via `auth/switch-context`, so no `X-Active-Role` header exists anywhere — the active context is inside the credential.

## Native platform rules

This app targets **Expo SDK 57** (`expo ^57.0.21`, `expo-router ~57.0.20`, RN 0.86, New Architecture, React Compiler on). It was on SDK 54 until the upgrade; version still matters more here than anywhere else in this file, so read `https://docs.expo.dev/versions/v57.0.0/` before writing navigation or layout code, and distrust any snippet written for 54 — several of the APIs below changed shape between the two.

**`expo@57.0.9` is a floor, not a preference.** SDK 55 with Hermes V1, all of SDK 56, and SDK 57 before that patch carry a Hermes memory regression that is triggered by `react-native-worklets` / `react-native-reanimated` — both of which this app has. Do not pin below it, and do not change the Hermes version from the SDK default.

**Application code must not import from `@react-navigation/*`.** From SDK 56 those go through Expo Router's own entry points, and the packages are no longer direct dependencies — two copies of `@react-navigation/native` in one tree is a navigation context that silently resolves to the wrong one. `@react-navigation/native` → `expo-router/react-navigation`; `@react-navigation/drawer` types → `expo-router/drawer`; `@react-navigation/bottom-tabs` → `expo-router/js-tabs`. `npx expo-codemod sdk-56-expo-router-react-navigation-replace <dirs>` does the mechanical part.

### Safe areas

**Android is edge-to-edge** — always, and there is no longer a key for it: `android.edgeToEdgeEnabled` was removed from the config schema (as was `newArchEnabled`) because both are simply how it is now. The app draws *under* the status bar and the navigation bar by default. Nothing is inset for you. Before edge-to-edge the system bars were translucent and content underneath them was usually fine; now an unpadded screen puts its first row behind the clock and its last button behind the gesture pill.

- **`useSafeAreaInsets()`, never `SafeAreaView`.** All four screens that handle insets already do this (`app/index.tsx`, `app/pilih-peran.tsx`, `app/kasir.tsx`, `app/(admin)/_layout.tsx`). The reason is that `SafeAreaView` spends the inset as padding on *itself*, which is wrong the moment the padded element scrolls: a list needs its bottom inset inside `contentContainerStyle` so the last row can scroll clear of the gesture bar, while the container itself must stay full-bleed so the list's own background reaches the edge. One hook gives you the number and lets you decide which of those it is.
- **An inset is applied exactly once, by whatever owns that edge — and "whatever" is a group layout, never the root stack.** `app/(admin)/_layout.tsx` pads **three** edges outside the native tab navigator — top, left, right — and leaves the bottom alone because native tabs handle it themselves: on Android each tab screen is wrapped in a `SafeAreaView` applying the bottom inset for the bar, and on iOS the first `ScrollView` in a tab gets automatic content-inset adjustment. A screen mounted in there must add neither: no `insets.top`, and no bottom inset for the bar.

  **`app/_layout.tsx` pads nothing at all**, so a section sitting beside the tabs on the root stack has to pay its own three edges. `app/produk/_layout.tsx` and `app/penerimaan-susulan/_layout.tsx` both carry that box, and the reason they exist is a bug: when those sections moved out from under `(admin)` they lost their insets in silence, and Android being edge-to-edge meant the header sat under the status bar and the docked button under the gesture pill. **Any new section placed beside the tabs needs the same box** — the root stack will not give it one, and nothing warns.

  The bottom edge on a root-stack section belongs to whatever it docks there — the green pill, the cart foot — which reads `insets.bottom` in the component, because an inset is a runtime value that changes with rotation, a foldable and the keyboard, and is often zero. Double-padding is invisible on a device with no notch and obvious on every device with one. A `Modal` is the exception and applies its own, because it is its own window and is not inside any padded box.
- **A shown native header already handles its own insets.** Everything here runs `headerShown: false`, so the screens do it themselves. If a header is ever turned on, drop the manual top padding under it; Android's native header insets every edge by default, and `unstable_headerInsets` exists only to switch that off.
- **All four edges, not just top and bottom.** `app/(admin)/kasir.tsx` no longer locks landscape, but it is still the screen most often *held* that way, and in landscape the notch is on the *side*. Those two edges are the group layout's job, as they are for every tab; what the POS owns is the **bottom**, because it hides the bar that would otherwise be padded for. It spends that inset three times, each by whatever owns the edge: the cart's totals foot, the keypad's CTA foot, and the product list's `contentContainerStyle` (tablet only — on the phone the docked cart is underneath it and owns the edge instead).
- **Insets are runtime values that change and are often zero.** Rotation, a foldable unfolding, the keyboard. Read them in the component; never bake one into a module-level `StyleSheet.create`.

### The keyboard is not an inset you get for free

**Under edge-to-edge the Android window is not resized when the IME opens.** The app keeps drawing at full height behind the keyboard and is expected to consume the inset itself. So the advice everyone reaches for — wrap it in a `KeyboardAvoidingView` with `behavior={undefined}` on Android — is an **empty wrapper in this app**, and anything docked on the bottom edge is covered with no way to reach it. That was a real, shipped bug on the login screen's "Masuk" button, and it was a real bug in every `RamahSheet`, which is the worst case of all: a sheet is anchored to the exact edge the keyboard arrives on.

`hooks/use-keyboard-height.ts` is the measurement, and it has two consumers:

- **`useDockPadding(insets.bottom, gap)`** is what a docked control uses instead of `insets.bottom + gap`. The two values are **alternatives, never a sum** — while the keyboard is up, the gesture bar that inset pays for is itself behind the keyboard, and paying both lifts the button by a strip of nothing. Every docked green pill in `produk/` and `penerimaan-susulan/` uses it.
- **`RamahSheet` does not use it.** It is the platform's own sheet now (see below), so the IME is handled by Compose and SwiftUI rather than by anything in this repo. Adding padding on top of what the OS is already doing would double-count it.

`KeyboardAvoidingView` is deliberately not used anywhere, and `ModalShell`'s comment claiming "Android already resizes the window for the keyboard" is **wrong** — it is a pre-edge-to-edge leftover. That dialog is centred so it degrades less visibly, which is why nobody caught it.

**What is still not handled: scrolling a focused field that is halfway down a long form into view.** Android's native ScrollView does it once the scroll view's bounds are right, which they now are; iOS does not, and neither does reliably inside a `Modal`. The fix for that specific gap is `react-native-keyboard-controller` — Expo's keyboard guide recommends it, `react-native-reanimated` is already here, and it needs `KeyboardProvider` at the root plus a **native rebuild**. It is a deliberate step, not something to add quietly.
- **A modal has to opt back into covering the bars.** `ModalShell` passes `statusBarTranslucent` and `navigationBarTranslucent` for this reason: without them the scrim stops short at each end, and a dialog that dims everything except a strip top and bottom reads as a rendering fault rather than as a layer over the app.

### Modals: three different things, and the choice is not cosmetic

Expo Router offers a route with a `presentation` option, and React Native offers a `Modal` component. They are not alternatives — they answer different questions, and the test is whether the thing being opened is *a place in the app*.

- **A dialog decided about the record already on screen used to be `ModalShell`** — React Native's own `Modal`, opaque and painted the page colour, with no invisible full-screen dismiss target behind it: a tap that loses your work needs something on screen to warn you, so closing was the dialog's own cancel control or the Android back button (`onRequestClose`). **It is gone now, deleted from `components/shell/ui.tsx` along with `ModalHead` and `ModalFooter`**: `components/pembelian/form.tsx` was its last caller, and issue #24 moved that sheet to `RamahSheet` with the rest of the section. Every dialog left in the app that is a question about a record already on screen is a `RamahSheet` — `components/shell/aksi-dialog.tsx` is one, shared by every document group — or a route, as the produk and pengaturan dialogs are. React Native's own `Modal` still appears twice for cases this rule never covered — not a dialog deciding about a record on screen: `components/pembelian/lampiran.tsx`'s full-screen photo viewer, and `components/shell/role-switcher.tsx`'s hand-drawn sheet, kept off `RamahSheet` so it can raise the same grant-switcher over both palettes.
- **A flow with steps somebody could link into is a route**, pushed normally. `baru.tsx` is the worked example.
- **`RamahSheet` is the platform's own sheet, through `@expo/ui/community/bottom-sheet`** — Jetpack Compose's `ModalBottomSheet` on Android, SwiftUI's sheet on iOS. That package is `@expo/ui`'s API-compatible replacement for `@gorhom/bottom-sheet`, which is no longer a dependency at all. **`@expo/ui` is a native module: adding it needed a dev-build rebuild (`npm run android`), and so will an SDK bump.** Two failed implementations are why, and both failures are the same shape — a sheet that depended on JavaScript having measured or reported something:
  - **`@gorhom/bottom-sheet` made every sheet in the app silently dead.** Pressing anything that opened one did nothing, on every screen, with no error. A sheet cannot open until `useAnimatedDetents` can say where its detents are, and that hook returns an **empty detent set** if the container height, the handle height, or (under `enableDynamicSizing`) the content height has not been measured. The container height is the fatal one: `BottomSheet` renders its own hosting container with `shouldCalculateHeight={!$modal}`, so a **modal** sheet measures nothing and reads from the single container `BottomSheetModalProvider` renders at the app root. One measurement shared by every `BottomSheetModal` there is; when it does not arrive they all die together.
  - **A plain `BottomSheet` inside an RN `Modal`** escaped that shared measurement and was worse: the window came up on `visible` and only came down when the sheet reported reaching index -1. Miss that one callback and a full-screen transparent window stays over the app forever — every control still drawn, none reachable. The app went dead to touch after the first sheet was dismissed.
  The native sheet has no measurement chain to stall; its host carries `pointerEvents="none"` while closed, and when closed it renders **nothing at all** — not the native view and not its children, which also took the sheets' contents off every render they used to sit on. No provider, no portal, no `GestureHandlerRootView` of its own. The `visible` / `onClose` / `title` API is unchanged, so no call site moved. **The one thing that did change on screen is the title, which is now in the body**: the platform draws the drag indicator, and `handleComponent` is documented as not rendered on native — drawing our own grabber under the system's would be two of them. `BottomSheetBackdrop`, `BottomSheetFooter` and the hooks are gone the same way; the scrim, the back button and the keyboard are the OS's now.
- **`presentation: 'modal'` / `'formSheet'` is for a route that should feel detached from the stack it came from** — a full-screen task over the tabs, or a sheet. Two things to know before reaching for it. A modal route *loses the context of the screen below*, which is why `unstable_settings = { anchor: 'index' }` is mandatory on any stack that presents one: a cold deep link into it otherwise builds a stack with nothing underneath, and dismissing leaves the app. And on Android a `formSheet` cannot render a native header or a nested stack, so `headerShown`, `title` and header buttons silently do nothing inside one — a sheet that needs a title draws it in its own content.
- **Nothing in this app blocks the back button.** There is no `BackHandler` anywhere, and there should not be: `app.json` sets `android.predictiveBackGestureEnabled: true` (`android:enableOnBackInvokedCallback`), so Android begins animating the screen away as the gesture starts, before JS gets a say. A confirmation that must happen before leaving belongs on an explicit action, not on an intercepted back.

### Native tabs: what they cost

The app is on native tabs. `expo-router/js-tabs` remains the escape hatch — the same React Navigation bottom tabs, reached through Expo Router now that `@react-navigation/bottom-tabs` is no longer a direct dependency — and the hand-drawn `RamahTabBar` that fed it is recoverable from git history. What using the platform bar actually costs:

- **It is alpha.** Expo's own docs still say "Native tabs is in alpha … Its API is subject to change", and the import path still carries `unstable-`. An SDK bump is a reason to re-read `app/(admin)/_layout.tsx`, not a routine upgrade.
- **Every tab mounts eagerly and cannot be made lazy** — the bar needs each screen present to animate between them, so all five roots fire their first read on launch rather than on first visit — Pendapatan's seven `laba-kotor` calls and Riwayat's first page included. Documented behaviour, not a bug to hunt. The two sanctioned deferrals are `useIsFocused` (unmounts on blur, losing scroll and form state) or a `useFocusEffect` "has been activated once" flag.
- **`hidden` on a trigger means unreachable**, which is what displaced `penerimaan-susulan` above.
- **Web falls back to a rough iPad-shaped bar.** If `npm run web` ever matters, the fix is a `_layout.web.tsx` using `expo-router/ui`, not styling.

The remaining notes below still hold:

- **The import shape is compound**: `import { NativeTabs } from 'expo-router/unstable-native-tabs'`, then `<NativeTabs.Trigger.Label>`, `.Icon`, `.Badge` inside `<NativeTabs.Trigger name="…">`. The flat `import { NativeTabs, Icon, Label, Badge }` form is the SDK 54 shape and is gone — any snippet using it is written for a version this repo is no longer on.
- **`VectorIcon` is imported from `expo-router` itself**, not from the native-tabs subpath, and takes an `@expo/vector-icons` family: `<NativeTabs.Trigger.Icon sf="house" src={<VectorIcon family={Feather} name="home" />} />`. `sf` wins on iOS and `src` is used on Android, so each platform gets its own vocabulary without the app carrying two icon sets. `md` (Material Symbols by name) is the alternative on Android and needs no vector-icon bridge at all.
- **Tabs are not added automatically.** Unlike `Stack`, every route needs an explicit `NativeTabs.Trigger`, and a tab marked `hidden` is unreachable by any means.
- **Every tab mounts eagerly and cannot be made lazy** — the native bar needs each screen present to animate between them. Three roots each firing their first page fetch on launch is the default behaviour, not a bug to hunt. `useIsFocused` (unmounts on blur, losing scroll and form state) or a `useFocusEffect` "has been activated once" flag are the two ways to defer expensive content.
- **Eager mounting also changes where "back" goes.** A tab containing a stack is already sitting on that stack's index before you link into it, so a detail pushed *inside* a tab lands on top of that tab's index — back returns there, not to the tab you came from, and `withAnchor` does not change it. **Push a detail from the stack that contains the tabs, not from inside a tab**, if back should return where the person actually was. That matches this repo's shape already: `app/_layout.tsx` is the outer stack.
- **Safe-area handling is automatic.** On Android the screen content is wrapped in a `SafeAreaView` applying the **bottom** inset for the bar; on iOS the first `ScrollView` in a tab gets automatic content-inset adjustment. `app/(admin)/_layout.tsx` therefore pads only top, left and right, and a screen inside must add neither that nor a bottom inset of its own.
- Tapping the active tab pops its stack to root, and tapping again scrolls to top, on both platforms. `disablePopToTop` and `disableScrollToTop` turn each off per trigger. On web, native tabs fall back to a rough iPad-shaped bar — if web ever matters that is a `_layout.web.tsx` with `expo-router/ui`, not a styling problem.

`homeRouteFor` in `services/permissions.ts` answers `/kasir` for a cashier and **`/beranda`** for everyone else — both of which are tab roots now, so it is also what the POS's own "kembali" uses, and a cashier correctly stays where they are. Beranda is the first root and the only screen that answers "what is most urgent today"; Katalog answers "how much of this is left", which is a question you arrive at rather than one you open the app on, which is why it stayed a pushed route rather than joining the bar.

### Performance levers, in the order worth pulling

- **`freezeOnBlur` is off.** It defaults to `false` unless `enableFreeze()` runs at app start, and nothing here calls it — so a section list keeps re-rendering underneath the detail pushed over it. That is fine at 20 rows a page, and is part of why lists keep their scroll for free. If a section ever profiles badly, `freezeOnBlur` is a per-navigator screen option and can be tried on one `_layout.tsx` without touching the rest.
**A list that appends pages is a `FlatList`, never a `ScrollView`.** A `ScrollView` mounts every row it has ever been handed and keeps them all mounted, which is fine for a fixed eleven and is a growing tax the moment the rows come from a paged endpoint. The till's catalogue was written as a ScrollView against a hard-coded array and kept that shape when it was wired to `GET /pos/product`; four pages in, eighty `Pressable`s were re-rendering on every keystroke in the search field. That, plus sheets that rendered their contents even while closed, is what made the app feel heavy. `onEndReached` is also the real affordance — an `onScroll` threshold computed by hand is a worse version of it, and neither is a guard: the in-flight boolean is.

- **`getItemLayout` and `removeClippedSubviews` are deliberately absent** from `record-list.tsx` — rows are not a uniform height, so a lied-about layout costs more than its absence. Do not add either without measuring first.
- **`onEndReached` fires repeatedly on one approach.** The in-flight boolean is the guard; `onEndReachedThreshold` is not one.
- **React Compiler is on** (`experiments.reactCompiler`). Do not hand-add `useMemo`/`useCallback` for render-count reasons — write the plain version and let it do its job. `useCallback` still earns its place where identity is part of an API contract, such as a `useFocusEffect` dependency.
- Testing any of this honestly needs a native build: `npm run android` / `npm run ios`, never Expo Go, because `react-native-bluetooth-classic` and `expo-secure-store` are native modules and both fail *quietly* in Go.

## Styling

Two palettes coexist, and that is the migration showing. `constants/theme-erp.ts` is the old blue-and-gold back office; **`constants/theme-ramah.ts` is the Ramah system, and it is the only place a Ramah value is written down.** Import from it — do not open a fresh `const D` block. The two screens that predate it (`app/index.tsx`, `app/pilih-peran.tsx`) still carry their own local blocks and are still the worked examples for *how* a screen is ported, but their hex is now a duplicate of that module rather than a second source.

**Do not promote the Ramah values into `theme-erp.ts` / `tailwind.config.js` / `components/ui/gluestack-ui-provider/config.ts` piecemeal** — those three hold the same old palette three times, are read by every screen that has not moved, and must be deleted together at the end rather than edited one value at a time. `theme-ramah.ts` sits beside them for exactly that reason.

### What revision 2 changed

The guide re-anchored on **daily merchant screens** — what a shop owner opens four times a day to check a number and fix a row — instead of consumer onboarding. The palette and type *family* are unchanged; the geometry is not.

- **The page is grey and the cards are white.** `surfaceSunken` is the canvas of every operational screen, and a stack of white `surfaceCard` blocks with hairline borders sits on it. One card, one subject: a card can be added, swapped or hidden per role without disturbing its neighbours. This replaces the full-bleed curved colour header — `CurvedHeader` is still legal, but only on a balance/wallet surface and in onboarding, never on an operational home.
- **The gutter is 16, not the token file's 24.** `RamahLayout.gutter`. Cards are 12 apart and 16 of internal padding, 12 when dense. The guide draws **16 between groups and 14 as dense padding; issue #31 overrode both** (24 and 12) — see "Spacing" below before reading the guide's numbers as the code's. The 24pt gutter survives only on the two consumer-shaped screens already ported.
- **Gradients are still banned, so a tint block does the header's job** — a flat `orange50` identity block flush to the top edge, no curve. **Shadows are no longer banned outright** — issue #32 replaced that rule with two elevation tokens for surfaces that float, see "Elevation" below. Everything that sits *on* the page still gets its depth from hairline, tint and the sheet scrim.
- **Forms invert the usual hierarchy**: a Caption label (12/16 Demi, grey) above a Title Small value (20/24 Bold), on a 1px underline rather than in a box (1.5px `borderFocus` when focused, no glow). A filled form then reads as a summary. Required is a red asterisk after the label — never the word "(wajib)". Errors are one flat caption line: "Isi angka lebih dari 0". Save is one full-width green pill docked at the bottom.
- **Exactly one solid green pill per screen.** Navy is structure and never a button; orange marks stock and is unreadable as body text (`orange500` is 2.2:1 on white — small orange text is `textWarning`, see "Typography"); red is required-and-wrong only, not a brand colour.
- **The type scale is 9 × 1.3 with line heights on the 4px grid, from 12/16 to 44/56**, named Title / Body / Caption, and **12pt is the floor with no exception** — see "Typography" below. The old "tops out at 22/26" and "13px floor" belonged to revision 2 and are gone.
- **The family is Poppins, and it is three families rather than one.** `tokens/fonts.css` names it (a documented substitution upstream) and the system spends three weights on it — Book 400, Demi 600, Bold 700; issue #33 dropped Medium — which are the three faces `app/_layout.tsx` hands to `expo-font`'s `useFonts` from `@expo-google-fonts/poppins`, behind the same splash screen that already waits on the session. **React Native does not synthesise a weight for a custom font**: Android resolves `fontFamily` to one registered face and then ignores `fontWeight` entirely, so a single "Poppins" family plus `fontWeight: '700'` renders regular, silently, on that platform only. `RamahWeight` in `constants/theme-ramah.ts` is the three named faces with their numeric weight kept beside them — the weight is what makes a failed font load merely plain instead of uniformly thin — and every `RamahType` bundle spreads one. **A raw `fontSize`/`fontWeight` pair in a screen's `StyleSheet` is a line of text in the platform font**; spread a `RamahType` bundle, or at minimum the matching `RamahWeight` beside the size. This is also why the runtime loader is used rather than the `expo-font` config plugin: the plugin takes the family from the file on iOS and from the file *name* on Android, which would put a `Platform.select` in every text style in the app.
- **Titles are tracked, body is not.** `--tracking-title` is −0.01em and Poppins is a geometric grotesque that needs it; React Native's `letterSpacing` is in points, so the em figure is multiplied out per size in `RamahType` — from Title Small (20) up — and nothing at or below 15px is tracked at all.
- **The old palette's screens keep the platform font**, the same way they keep the old palette. Poppins arrives with `theme-ramah` and lands on every ported surface plus `components/shell/role-switcher.tsx`, which is raised over ported and unported screens alike and would otherwise be one control that looks like two. `tailwind.config.js` is deliberately untouched: NativeWind's `font-*` classes set a weight, not a face, so pointing `font-sans` at one Poppins file would flatten every gluestack heading in the back office to regular.
- **Four icon sizes** (14 counter / 16 metadata / 20 row and tile / 24 header) and four radii (16 card, 14 tile squircle — the guide's number, not the token file's 20 — 12 field and dense card, 999 pill).
- **Every operational number carries when it was read and how to re-read it.** `stempelPembaruan()` formats the stamp; the guide's reason is that a number with no time on it cannot be told from a stale one.
- **Shortcut-tile colour is fixed by function, not chosen per screen** (`RamahTileTone`: stock orange, catalogue blue, documents navy, reports sky, suppliers amber, account grey). Someone who opens this app forty times a week stops reading labels and goes to the orange one, which only works if orange means stock everywhere.

Two things in the guide contradict themselves and are worth knowing before you follow either: §4 draws the shortcut tile as a bare 52px 3D icon with no squircle, while §8 specs it as a 28px icon inside a 44px squircle, and §9's "tidak diambil" list still says 3D icons were rejected in favour of tinted squircles — which §8 reverses. **§4 is the newer drawing, and it is what `RamahTile` implements**, because `LayarGudang.dc.html` draws it §4's way too: the asset alone at 52px, no squircle, no tint, `resizeMode="contain"`.

### Spacing: one 4px grid, and a gap is a statement (issue #31)

**Every `padding`, `margin` and `gap` on a Ramah screen is a multiple of 4 and comes from `RamahLayout`.** Distance is how a reader tells what belongs together — nearer is related, further is not, an identical gap pattern reads as equal weight — so a 10 beside a 12 beside a 14 is noise that blurs the grouping, not three careful choices. The only things allowed off the grid, listed at `RamahLayout` itself: hairlines (1, 1.5), sizes rather than gaps (`controlH`, `rowH`, `tapMin`, icon sizes), radii, and a 1–3px optical nudge centring a drawn glyph or a checkbox against a line of text (the three `marginTop: 1` on pickers' checkboxes and radios, the `AppShell` chevron). The check is the issue's own:

```
rg -n "(padding|margin|gap|rowGap|columnGap)\w*: *\d+" app components/shell components/pembelian components/pemasok components/pengaturan
```

— zeros, those four nudges, and `app/index.tsx` / `app/pilih-peran.tsx`, which keep their old local palette and gutter and are out of scope.

**Five semantic tiers name the relationships, and a screen reaches for them first**: `inline` 4 (two parts of one fact — label ↔ value, title ↔ subtitle), `related` 8 (equal items in a group — chips, side-by-side buttons, icon ↔ label, a heading ↔ the card it names), `stack` 12 (cards in one group, controls stacked over a list), `group` 24 (groups about different things), `section` 32 (around the one thing a screen is for). The raw `space*` scale stays as the ruler for a component's own interior — a pill's side padding, a row's icon gap. **The rule the tiers exist to keep: the gap between groups is clearly larger than any gap inside one.** `stack` 12 against `group` 24 is a 2:1 step.

**This departs from `Panduan Gaya.dc.html` revision 2 on purpose, and the guide was not edited to match**, so the two disagree in these places and the code wins: groups 24 (guide: 16, only 4pt from the card gap, which reads as one distance twice on a phone); `cardPadDense` 12 (guide: 14 — down rather than up, because dense rows are what portrait runs out of first); `tileGapY` 16 (guide: 14 — vertical costs a four-column grid nothing across); `metricGap` 16 (guide: 14); and a new `dockPad` 16 above and below every docked action, which used to be 10 or 12 depending on the screen.

**`RamahSectionHeader` carries no padding at all, and whatever holds it owns the distance.** It used to have 20 above and 8 below, which was right only in the container it was first drawn in: in a 16pt column it sat 24 from its own card and 36 from the group before it. Three shapes, each with its worked examples:

1. **A column of wrapped groups** — body `gap: L.group`, each group a `View` with `gap: L.related`, heading first. The detail screens: `app/produk/[id]/index.tsx`, `app/pembelian/[id].tsx`, `app/penerimaan-susulan/[id].tsx`, `app/penjualan/[id].tsx`.
2. **A `stack` column with loose headings** — the heading wrapped in a `groupStart` view, `paddingTop: L.group - L.stack`, so it opens 24 below what came before and its cards stay a `stack` under it. `app/laporan/index.tsx`, `app/(admin)/pendapatan.tsx`, `app/pengaturan/[id]/index.tsx`, `app/pengaturan/ruang/[id]/index.tsx`, `app/pemasok/[id]/index.tsx`, `app/stok-opname/baru.tsx`; Beranda and Profil put the same `marginTop` on the group itself.
3. **Headings as `FlatList` items** — `listHeading: { paddingTop: L.group - L.stack, paddingBottom: L.related }`, with `cardLast` leaving `marginBottom: L.stack` and the list's controls `paddingBottom: L.stack`, so every heading lands at `group` whatever precedes it. `app/produk/index.tsx`, `app/(admin)/riwayat.tsx`, `app/stok-opname/index.tsx`, `components/pembelian/pilih-pemasok.tsx`, `components/pembelian/pilih-barang.tsx`. Where the heading is instead the last of a list's controls (`app/stok-opname/[id].tsx`, `app/laporan/pergerakan.tsx`) it takes `groupStart` and the controls drop to `paddingBottom: L.related`.

A heading dropped bare into a column now sits at that column's gap from both neighbours — equally close to what it names and to what it does not — so do not.

**Hierarchy is spent where the screen's purpose is, and density is kept where it is the point.** The docked pill gets `dockPad`; Kasir's success card gets `section` all round; Beranda's metric card gets 16 rather than 12 under the orange block, and its metric/score pair is one group with the feature grid and invoice preview each a group of their own. The keypad, the docked cart's rows (8 vertical) and catalogue rows stay tight. **Kasir's key gap is 8 on both layouts** — one keypad at two sizes — and the compact `wideKeyH` arithmetic reads it as `3 * L.space2`, so change the two together.

### Elevation: two tokens, and only for what floats (issue #32)

Revision 2 banned shadows outright, and it cost one thing it could not afford: a surface *over* the content could not be told from one *in* it. Every docked "Simpan" pill was separated from the list scrolling behind it by one `#EBEBEB` hairline, which vanishes the moment a white row passes under it. **`RamahElevation` in `constants/theme-ramah.ts` holds exactly two shadows, `low` and `high`, and is the only place a shadow value is written.** `rg -n "shadow(Color|Offset|Opacity|Radius)|elevation:|boxShadow" app components` should find nothing outside that token.

- **A shadow states position on the z-axis, never importance.** The green pill gets no shadow to stand out — colour does that. Cards, rows, chips, tiles and fields get none either: white on `surfaceSunken` already separates a card, and a card is the page, not something over it. No coloured glow, no shadow on text or icons, and a shadow is never animated except along with the surface that casts it.
- **The light falls straight onto the screen**, so both tokens are offset 0,0 and spread evenly on every side; the only difference is size. `low` (blur 12) is one layer over the content; `high` (blur 32, spread 4) floats clear of the layout. The ink is navy at 12% / 16%, the same hue as `scrim`, not black.
- **Who gets which:** every bottom dock, and Kasir's cart foot, keypad foot, docked phone cart and its totals foot, are `low`. `components/shell/role-switcher.tsx`, the one hand-drawn floating sheet, is `high`. `RamahSheet` gets nothing — the native sheet already draws the platform's own elevation, and Kasir's `more-vertical` menu is one of those. A future popover or toast is `high`.
- **A surface that takes a token loses its hairline on that edge** — two depth cues for one edge is one too many. `app/produk/baru.tsx`'s confirmation dock is the one dock without a token, for the reason it never had a hairline: nothing scrolls under it.
- **It is `boxShadow`**, the CSS model with spread and colour, drawn alike on both platforms under the New Architecture — not Android's `elevation` (no spread, colour ignored on most devices) and not the iOS-only `shadow*` quartet. Two things bite. It draws nothing behind a surface with no opaque `backgroundColor`, which is why Kasir's feet gained `surfacePage`. And **Android only draws an outset `boxShadow` from Android 9 (API 28) while `minSdk` is 24**, so below 9 each token falls back to the hairline it replaced — a top line for `low`, whose surfaces all sit on the bottom edge, a ring for `high`. An old phone keeps the pre-#32 look instead of losing the separation.

`Panduan Gaya.dc.html` §7 and `tokens/elevation.css` in the Claude Design project were updated to say the same, so the guide and the code agree again on this point.

### Typography: 9 × 1.3, three weights, AA contrast (issue #33)

**`RamahType` is derived, not picked.** A 9pt base times 1.3 per step, rounded to a whole point, with a line height of size × 1.3 rounded to the **nearest multiple of 4** — so text sits on the same grid as spacing (issue #31). The steps: 12/16, 15/20, 20/24, 26/32, 34/44, 44/56. n=3 was a tie between 24 and 28 and took 24, because it is a field's value and a group heading and both stack in dense forms. A new size is the next step, never a number between two — `rg -n "fontSize: *[0-9]" app components/shell components/pembelian components/pemasok components/pengaturan` finds nothing outside `app/index.tsx` / `app/pilih-peran.tsx` (old local palette, out of scope).

**Names are the hierarchy, shared with the guide**, not a screen's role:

| Token | Size / LH | Weight | For | Replaced |
|---|---|---|---|---|
| `titleHero` | 44/56 | Bold | one number with a screen to itself | — |
| `titleLarge` | 34/44 | Bold | a metric, the till's readout, kembalian | `metric` |
| `titleModerate` | 26/32 | Bold | business name, page heading, a sale's total | `identity` |
| `titleSmall` | 20/24 | Bold | group heading, a field's value | `groupTitle`, `fieldValue` |
| `titleTiny` | 15/20 | Demi | a row's title, every button label | `rowTitle` |
| `bodyModerate` | 15/20 | Book | a sentence | `body`, `subtitle` |
| `bodySmall` | 12/16 | Book | a short sentence, the metadata line under a title | old `caption` |
| `caption` | 12/16 | Demi | a field's label, a tile's label, a status pill, a counter | `fieldLabel`, `delta`, `micro` |

**Mind the name that moved: `T.caption` used to be 12/17 regular and is now 12/16 Demi.** Everything that was the old caption became `bodySmall`; the new `caption` is what was `fieldLabel`/`delta`/`micro`, and it is meant to be used sparingly. Tracking is −0.01em from Title Small up, multiplied out per size; nothing at 15 or below is tracked.

- **Three weights: `RamahWeight.book` / `demi` / `bold`** (Poppins 400 / 600 / 700). Medium is gone, and `Poppins_500Medium` is no longer loaded. **No italic** anywhere.
- **12pt is the floor with no exception.** The old 11px tile-label tier is Caption now.
- **The family stays Poppins.** Aloha's own rule is that the typeface is chosen with the brand team, and its face (Maison Neue) is Gojek's licensed brand identity; this app took the system, not the face.
- **`RamahPrimaryButton` takes `type`, a `RamahTypeName`, instead of a raw `fontSize`** — Title Tiny by default, Title Small / Moderate on the till's pay button — so a label can only be a size on the scale and always brings its own line height.
- **Kasir's `fontCap` still caps growth by size**, and its thresholds are scale steps now (20 = Title Small, 15 = Title Tiny). There is still no `allowFontScaling={false}` anywhere.

**Every text colour clears WCAG 2.0 AA — 4.5:1, or 3:1 for Title Small and up — on every light surface it can sit on**, and the table of ratios is a comment above the text tokens in `constants/theme-ramah.ts`. Test a new text colour against the same surfaces before adding it. What that changed:

- **`textMuted` failed everywhere (2.33–2.78) and is now `#6A6A6A` — the same ink as `textBody`.** No grey lighter than body clears 4.5:1 on `grey200`, so the name survives for the *role* (metadata, stamps, counts) and hierarchy between the two is carried by size and weight. `textBody` moved from #6B6B6B to #6A6A6A for the same reason.
- **`textDisabled` (#9B9B9B) is the one grey below 4.5:1**, allowed because WCAG exempts a control that cannot be used: a disabled tile, a locked or read-only field. Never for anything a reader acts on.
- **`textDanger` is #D01E1E**; `danger` (#E02020) stays the fill and border colour. The required asterisk is text, so it takes `textDanger`.
- **Small orange text is `textWarning` (#9E5913, the new `orange700`), small amber text is `amber700`.** `orange600` / `amber600` stay for icons and for text at Title Small and up; `orange500`, `warning` and `info` are never text.
- Icons, hairlines and fills are not text, and keep their lighter values. The native tab bar's unselected *label* is `textMuted` while its icons stay `iconMuted`.
- `components/shell/role-switcher.tsx` keeps the old palette but not its failing greys: `muted2` became `muted3`, and the check mark `primaryDark`.

What issue #33 asked for and this pass did **not** do: sift the ~160 former `T.caption` lines one by one for which could be deleted (#27's spirit). They were mapped mechanically to `bodySmall`; that sift is still worth a screen-by-screen pass.

### The feature tiles' 3D art

The renders are vendored now, in `assets/icons-3d/`. They come from IconScout — contributor **Iqonic Design**, pack **Ulta Bizz** (15 items, free for commercial use), with *Bizzy Vol.2* as §8's fallback for analytics concepts. Pull them with the IconScout MCP, and mind the four rules the guide sets, each of which bites:

- **Ask for `png` explicitly.** The default download format for a 3D asset is `compressed-glb`, which is a model, not an image. 500px for the grid, 1000px only for a denser surface; transparent ground.
- **Square 2000×2000 sources only.** The pack's "B 2 C" and one of its two "Bank" renders are 3000×2000 and go flat, or need hand-cropping, in a uniform grid.
- **One concept, one icon.** Fifteen items are only about nine ideas — four *report* variants, two *bank*, two *B2C*. Two features wearing near-twins is worse than one of them going without.
- **Never recolour a 3D asset.** What adapts to the palette is the tile's surroundings, not the render.

**A gap is closed by a family, never by an orphan.** §8 checked both Iqonic packs and names three merchant concepts neither covers — kelola produk, pesanan masuk, chat pelanggan — and says to hold them on a Lucide line glyph over the matching `RamahTileTone` tint until they are re-rendered from the packs' `.blend` files. The beranda grid no longer has any glyph tiles (see "Where this repo actually is"), and that is **not** a licence to go shopping: what makes a grid look broken is mixing render *languages*, and a language is a whole pack's worth of camera angle, bevel weight and light direction. Adding one lookalike from an unrelated pack is the thing to refuse; adding a second whole pack, as the four logistics renders did, is not. `RamahTileArt` still encodes both shapes — `art3d` for a real asset, `glyph` for a documented gap — and `glyph` stays because the situation will recur.

### Mechanics that bite

- **A colour class has to be declared in `tailwind.config.js`, provider variable or not.** The semantic tokens (`card`, `background`, `foreground`, `border`, `muted`, `primary`, `destructive`…) take their *values* from the provider's CSS variables, but Tailwind still has to know the name — they are declared as `rgb(var(--token) / <alpha-value>)`, which keeps the runtime value and the `/70` opacity modifiers both working. **An undeclared class does not warn: it compiles to nothing, and the surface renders with no background at all.** Every dialog was see-through for exactly this reason.
- Colours resolve at build time, so a runtime-computed hex has to fall back to inline styles and drifts off the palette. Pass a `className` the caller picks instead.
- The palette is **opaque throughout**. Tints are pre-composited against white and written as hex rather than left as `rgba(…, 0.1)`, which is a different colour over every surface it lands on. Translucency survives only where it is the effect itself: a modal scrim, an edge fade.
- **`Pressable`'s `style={({ pressed }) => …}` callback silently does nothing in this app.** `babel.config.js` sets `jsxImportSource: 'nativewind'`, so every `Pressable` is the cssInterop wrapper, which normalises a non-array `style` by wrapping it in an array — and React Native only calls `style` when it is a function *itself*, never one nested inside an array. The function is dropped by `StyleSheet.flatten` and the element renders **with no styles at all**. Hold press feedback in state via `onPressIn`/`onPressOut` instead. Three screens have already tripped over this.
- **`flexShrink` defaults to 0, and on Android a child drawn outside its parent cannot be tapped.** Those two are one bug, not two, and `app/(admin)/kasir.tsx` shipped it: the docked cart carried `maxHeight: 320` while its head, its row list and its totals foot all sat at React Native's default `flexShrink: 0` (CSS's default is 1), so nothing shortened — the box was capped and its contents kept their full height and ran out of the bottom of it. On a device that looks like a pay button and the last cart rows **drawn but dead**, because Android's hit test stops at the parent's rect. The fix shape: cap the *scrolling* region rather than the box around it, and give that scroll `flexShrink: 1` so it is the thing that gives way. When a column can genuinely run out of room the shrinker has to be named — a sibling with `flex: 1` will not volunteer, because its flex basis is already 0 and there is nothing in it left to take.
- **`flexWrap` over a percentage width is not a grid.** The till's keypad was twelve `width: '31%'` keys in one wrapping row, which holds only while the gaps are small next to the column. At the 905pt breakpoint the keypad column is pinned to its own 300pt minimum, and 3 × 80.6 + 2 × 10 comes to 261.8 in 260 of content — one and a half points, and the pad silently became six rows of two with `Del` alone at the bottom. Rows of exactly N `flex: 1` children cannot do that at any width.

## Layout economy

The screens are read on a phone held in one hand, usually standing in a storeroom. **Every line of text on screen has to be one somebody would act on.**

- **A field that says the same thing on every row is not a field.** "Stok minimum" on the product list was a threshold with no reading beside it (the list payload carries no stock at all); "Diterima lengkap" on nine purchase rows out of ten buried the one that said "Kurang" — that one is now printed *only* when it is true. Reference data — NPWP, an address — is what you read once you have found the record, so it belongs on the detail, not in a row you scan.
- **Chrome that repeats on every screen earns its place once, not everywhere.**
- Prefer the shorter of two true phrasings ("Kurang", not "Kiriman kurang" under a label already reading "Kiriman"), and never print a count the neighbouring value already contains.
- **Do not invent a number to fill a card.** Revision 2 of the style guide promotes the score card to a documented pattern (§4: one figure, "/ 100", a short blameless sentence, a tint band by threshold), and `scoreTone()` encodes the bands — **the pattern being blessed does not conjure the data.** Nothing in `contracts/openapi.yaml` computes a stock-health score, so "94/100" stays unbuildable until something does. The real answer to "what is most urgent today" is a queue that exists — `product/stok-minimum` for whoever reorders, `pembelian?status=DIAJUKAN` for whoever posts. The same test applies to the two-metric card: two real numbers, or one card.

## Responsive rules

`hooks/use-breakpoint.ts` is the only place layout width is classified: `phone` / `tablet` / `large` at 600 and 905 (Material window size classes). Decide on **width, never orientation** — `height >= width` reads a portrait tablet as a phone. Use `atLeast(bp, 'tablet')`, and keep the breakpoint a string so it is safe in a dependency array.

A phone in portrait has ~354pt of content width, which is why fixed-width table columns do not fit. Prefer `minHeight` over `height` on anything wrapping text, so a raised system font size cannot clip it.

**Width picks the class; it does not on its own license a layout.** A window can clear a threshold on width and have nothing like the height the wide arrangement needs — a 20:9 phone turned sideways is **936 × 432**, past the 905 mark with 432pt of vertical room. `app/(admin)/kasir.tsx` shipped that bug: three columns, each pinned to its minimum width, product names cut to "Kertas H…", and a keypad clipped after its second row. Its `wide` is `atLeast(bp, 'large') && winH >= POS_COLUMNS_MIN_H` now, with the 640 counted off the tallest column's own stack rather than guessed. If a layout has a load-bearing tall dimension, test for it — and count the number, do not pick one.

**A screen never gets the whole window's width.** `app/(admin)/_layout.tsx` spends `insets.left` and `insets.right` outside the navigator, so what a screen inside it is laid out in is `width - insets.left - insets.right` — up to ~70pt less on a device with a landscape cutout, while `useBreakpoint()` still reports the full window. A row of fixed or `minWidth` columns that adds up to more than that box does not wrap: **a flex row overflows to the right**, and on a screen there is nothing to the right. Leave the minimums room, or the last column leaves the display.

**Which of the two thresholds a screen switches on is a judgement, and both are in use.** `atLeast(bp, 'tablet')` is the usual one. `app/kasir.tsx` switches at `large` instead, because its wide layout is three columns rather than two and the drawing's own widths need ~900pt before the middle one is a list rather than a gutter. Say which you picked and why at the call site; the number itself always comes from this hook.
