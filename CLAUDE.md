## Commands

- `npm start` — Metro dev server, then pick a platform.
- `npm run android` / `npm run ios` — **native builds** (`expo run:*`), not `expo start --platform`. The app needs a dev build: `react-native-bluetooth-classic` and `expo-secure-store` are native modules, and in Expo Go the printer reports itself unavailable and sessions silently fall back to memory-only.
- `npm run web` — `expo start --web`.
- `npm run lint` — `expo lint`. Baseline is **0 errors, 18 warnings**, all pre-existing `import/no-duplicates` and unused-var warnings inside `components/ui/*` (vendored gluestack). Treat any warning outside those files as yours.
- `npx tsc --noEmit` — not a package script, but the only real check on a repo with no tests. Run it before claiming a change works.
- `npx expo export --platform android` — the closest thing to a build test. Recent bundles are ~5.6 MB; a sudden jump means a dependency got pulled in.
- `npx openapi-typescript contracts/openapi.yaml -o types/api.ts` — after any contract change.
- `npx expo prebuild --platform android` — after touching `app.json` plugins. A JS reload is not enough.

No test runner is configured. `npm run reset-project` moves `app/` aside and leaves a blank one — it is a leftover from the `create-expo-app` starter. Never run it.

## The contract is the source of truth

`contracts/openapi.yaml` describes a backend this repo does not own, and `types/api.ts` is generated from it. **Check the contract before designing anything that depends on a filter, a sort, or a field.** Several plausible-sounding features are not buildable and the gaps are not obvious from the screens:

- `GET /product` accepts only `page`, `size`, `search`, `is_aktif`. No sort parameter, and the list payload carries no stock at all — fetching stock per row is the N+1 the contract explicitly warns against.
- There is no `DELETE /product`. The only removal is `PATCH { is_aktif: false }`, which is why archiving is treated as reversible everywhere.
- "Low stock" is a **separate endpoint**, `GET /product/stok-minimum`, pre-sorted worst-first — not a filter on the product list.
- Paging is offset-based (`page`/`size`) with no cursor anywhere, so appending pages must de-duplicate by id.

When the contract cannot serve something, say so rather than faking it client-side.

## Auth, session, and permissions

Three layers that only make sense together:

1. `services/session.ts` holds the one signed-in session. A session has a token **and** an `active` context (the chosen grant). `hasActiveContext()` is the type guard that narrows to `ActiveSession`.
2. **Routing is guarded by `Stack.Protected` in `app/_layout.tsx`, not by redirects in screens.** Three states, because this contract has one more than the usual pair: signed out (`index`), signed in with no grant picked (`pilih-peran`), and signed in with an **active context** (`(admin)` and `kasir`). A guarded-off route is not in the navigator at all, so a deep link cannot reach it and losing the session unmounts whatever is open. There is no `useRequireSession` any more — it redirected from an effect, which meant mounting, fetching against a dead session, and painting a frame first.
   `index` is deliberately unguarded: it is the anchor every closing guard falls back to, and the one place that knows a cashier's home is `/kasir` and everyone else's is `/produk` (`homeRouteFor`). It answers with `<Redirect>` rather than a `router.replace` in an effect. **Nothing signs out by navigating** — `logout()` drops the session and the guards do the rest.
3. `services/permissions.ts` — `useCanWrite(area)` / `useActiveRole()`. Roles are exactly `SUPERADMIN | INVENTARIS | CASHIER`; writes are split by **who owns the data**, not seniority. There is no `ADMIN` or `STAFF` in the contract.

`services/permissions.ts` stops at the *entry* permission for a screen. Documents with an approval flow split further along the flow rather than along the data: `INVENTARIS` types and submits, `SUPERADMIN` posts, rejects, and cancels, because posting appends to an append-only `kartu_stok` and can only be reversed, never corrected. `services/alur-dokumen.ts` holds the vocabulary — `StatusAlur`, `AksiDokumen`, `pilihAksi` — and each document module holds **its own `AKSI` table**: one row per transition, with the status it starts from and the roles the server accepts. The screen renders only what the active grant can actually run. `pembelian`, `penerimaan-susulan`, and `retur-pembelian` all run the same four transitions with the same role split, and the tables are still three, because the sentence each one shows before an irreversible write is the point: posting an invoice values stock at the invoice, posting a susulan copies the harga pokok the invoice already fixed, posting a retur takes goods back out at today's moving average. Copy that shape for the remaining document modules rather than growing `permissions.ts`. `components/pembelian/aksi-dialog.tsx` is shared by all three and knows nothing about which document it is confirming — every word it shows comes off the `AksiDokumen` it is handed.

`services/client.ts` single-flights token renewal because refresh tokens are rotated and deleted on first use — two concurrent requests must not spend the same one. Do not add a second refresh path.

## Screen architecture

- `app/(admin)/_layout.tsx` is a **`Drawer` from `expo-router/drawer`** (React Navigation's `createDrawerNavigator`, hence the `@react-navigation/drawer` dependency) with one screen per section, generated from the `NAV_ITEMS` array `components/shell/AppShell.tsx` also renders the menu from. The navigator owns the panel, the dimming overlay, the swipe-from-the-edge gesture, the animation, and the back-button handling; `AdminDrawerContent` only draws what goes inside the panel, and `AppShell`'s hamburger dispatches `DrawerActions.toggleDrawer()`, which bubbles up from whatever section stack it is called in. **Do not hand-roll this again** — the sidebar used to be a `navShown` boolean over two absolutely positioned views, which meant no swipe, no animation, and a menu that had to read `usePathname()` to know where it was.
  - **The drawer stops at the section root.** A section is a place you can leave; a record open on top of it is not. Once `[id]` or `baru` is pushed the menu is out of reach — the edge swipe is off (`swipeEnabled` in the drawer's `screenOptions`, from `getFocusedRouteNameFromRoute(route)` reading the section Stack nested in that route) and `AppShell` swaps the hamburger for the back chevron.
  - **That swap is driven by the `onBack` prop, not by the navigation state, and it must stay that way.** `AppShell` read `useNavigationState((s) => s.type === 'stack' && s.index > 0)` first, which is correct and *late*: a native-stack pop reaches the JS navigation state only when the transition ends, so for the whole animation the list underneath still believed it was at depth and its header showed a hole where the hamburger goes, filling in a beat after the screen settled. A prop is known at first render, so the bar is right on the frame it is drawn. Every depth screen passes `onBack` already — it is how it gets a back control — and no section root has anything to go back to, so the two sets are the same one. `swipeEnabled` still reads the route because it is a navigator option, and it only gates a gesture nobody can attempt mid-animation.
  - Safe-area padding is applied by a plain `View` **outside** the navigator, so the panel and its overlay are drawn inside the padding box: the drawer starts below the status bar and stops above the gesture bar, exactly as the content does.
  - The panel's width, background, border, and `overlayColor` are `screenOptions` on the navigator, not classes — they are read at runtime by the navigator, not by Tailwind, so they come from `constants/theme-erp.ts`.
- **A detail view or a create form is a route, not a `view` branch.** Push it (`router.push({ pathname: '/produk/[id]', params: { id } })`) and let `router.back()` return. Every branch faked with `useState` was an Android back button that exited the section instead of going back, a record with no URL to deep link, and a scroll position restored by hand. Reach for `Slot` only where a layout genuinely has to mount chrome without adding a level of history.
- **Section layout: `<section>/_layout.tsx` + `index.tsx` + `[id].tsx` + `baru.tsx`.** The `_layout.tsx` is a `Stack` with `headerShown: false`, `export const unstable_settings = { anchor: 'index' }`, and all three routes declared as `<Stack.Screen>` rather than left to the file tree: `index` takes `animation: 'none'` (it is the drawer's screen for the section, so the drawer already animated that move), `[id]` and `baru` take `slide_from_right`, and each carries a `title` — nothing draws it, but it is what names the route to the web document title and to accessibility instead of the file name. This is what keeps the drawer from flattening the depth: a section is one drawer screen, and the Stack inside it is where the detail and the form are pushed. The anchor is not optional — without it a cold deep link to `/produk/12` builds a stack with nothing underneath, and `router.back()` leaves the app. `laporan` and `unit-kerja-ruang` have no depth, so they stay single files with no layout. Conventions the sections now share:
  - Editing stays a **dialog on the detail** (the record is already on screen); the list's "Ubah" action pushes `[id]` with `?ubah=1`. Creating is the `baru` route, and it lands on the new record with `router.replace` + `?baru=1`, so back goes to the list and the detail does the announcing. Both parameters are read **once** into a ref on the way in — they seed the screen, they do not drive it. The dialog is `ModalShell` in `components/shell/ui.tsx`, which is React Native's own `Modal` — the split Expo documents: a dialog decided about the record already on screen is not a place in the app and wants no URL, while a flow with steps to link into is a route (`presentation: 'modal'` on a `Stack.Screen`), which is what the `baru` routes already are. `transparent` on that `Modal` is not a colour: it is what stops the modal *window* painting over the app, so the scrim and the opaque card can be drawn inside it. `onRequestClose` is what answers the Android back button.
  - **The way back lives in the header bar, not in the body.** `AppShell`'s leading slot holds the hamburger at a section root and a back chevron once anything is pushed over it — it already reads the depth off the navigation state, so a depth screen just passes `onBack={goBack}` and its **own** `title` (the record's number or name, not the section's). That is the arrangement every navigation bar uses, App Store included, and the reason is that the title and the way back describe the same screen. What is left in the body is the record's *status*.
  - **A detail's standing actions go in `headerRight`, as icons** (`IconAction` in `ui.tsx`, Feather via `@expo/vector-icons`). They are the same two on every record of a section — edit, and archive — which makes them chrome, not content, and a row of bordered text buttons above the record wrapped on a phone for no gain. Archive is `trash-2` in the danger colour and flips to `rotate-ccw` in primary on an archived record: the contract has no `DELETE`, so the bin means "out of the way", and the way back is the same button pointing the other way. Every icon carries an `accessibilityLabel` — an icon alone is a guess.
  - What does **not** become an icon: a one-off action whose label is the whole point. `pembelian/[id]`'s Ajukan / Posting / Tolak / Batalkan are role-filtered transitions that read differently to each grant, and "Terima pelunasan" is not guessable from a glyph. Those stay text buttons in the body.
  - Every detail and form has `goBack()` = `router.canDismiss() ? dismiss() : replace('/<section>')`. **`dismiss()`, never `back()`** — `dismiss` targets the closest `Stack`, which is the section's own, while `back()` is offered to the drawer first and a drawer holding an earlier section in its history answers it by switching sections instead of popping the screen. The `replace` covers a deep link with nothing to pop at all.
  - A detail reached cold must render a **failure page**, not toast over a list that may not be behind it.
- Cross-route state has exactly two shapes. `hooks/use-record-bus.ts` carries writes from a detail back to the list that is still mounted underneath it (`saved` patches one row, `reload` re-reads page one); each API-backed section declares its bus next to its row type (`produkBus`, `pelangganBus`, `supplierBus`, `pembelianBus`, `susulanBus`, `returBus`). `hooks/use-local-store.ts` + `stores/*` hold the seeded datasets for the three sections with no endpoint yet — they used to be a screen's `useState`, which two routes cannot share. Neither is a query cache, and neither should grow into one: when an endpoint lands, its `stores/` file is deleted, not extended.
- `app/kasir.tsx` is standalone: its own palette (`const K`), its own landscape lock, no `AppShell`. It also shadows RN's `Text` with a wrapper applying a size-derived `maxFontSizeMultiplier` — dense POS chrome cannot absorb a blanket 1.4× cap, so the cap goes *down* as the text gets bigger. Keep using that local `Text`.
- `app/index.tsx` is the login form **only**: one 420pt column, a fixed type scale, `minHeight` on the field and the button. It used to port the web design's `clamp(min, Nvh, max)` sizing through a local `useFluid()`, which tied the type scale to the *window height* — a 34px heading and 73pt fields on a tall phone, 54px and 96pt on a tablet, in a card capped at 920pt wide. Two fields and a button do not get easier as the screen grows; only the air around them should change. The grid of six illustrated role cards it used to open on is gone: it was tapped before authenticating, never reached the server, and four of its six names (`ADMIN`, `GUDANG`, `PEMBELIAN`, `SUPERVISOR`, `OWNER`) are not roles this contract has. Its SVGs are still in `assets/images/login/` and are now unreferenced.
- `app/pilih-peran.tsx` asks which grant to work as, and most people never see it: one usable grant is activated server-side during login, and a choice made before on this device is resumed silently (`resumeLastGrant`, remembered per user id in `services/session.ts`). It is a plain list, not cards — it is a decision taken about once a month.
- **The active role is permanent chrome, and switching does not go through logout.** `components/shell/role-switcher.tsx` exports `RoleChip` (in the `AppShell` header, on depth screens too) and `RoleSwitcherSheet` (also opened from the kasir menu; it is `StyleSheet` + `constants/theme-erp` rather than NativeWind precisely so kasir, which has its own palette, can use the same one). The chip is a label, not a button, for the majority who hold one grant. A switch issues a **new token** via `auth/switch-context`, so no `X-Active-Role` header exists anywhere — the active context is inside the credential. It also invalidates every list at once (a grant carries a unit kerja), which is what `reloadAllRecords()` in `hooks/use-record-bus.ts` is for, followed by `dismissAll()` + `replace(homeRouteFor(...))`.

## Layout economy

The screens are read on a phone held in one hand, usually standing in a storeroom. **Every line of text on screen has to be one somebody would act on.** Two rules follow, and both have already had to be applied once:

- **A field that says the same thing on every row is not a field.** "Stok minimum" on the product list was a threshold with no reading beside it (the list payload carries no stock at all); "Diterima lengkap" on nine purchase rows out of ten buried the one that said "Kurang" — that one is now printed *only* when it is true. Reference data — NPWP, an address — is what you read once you have found the record, so it belongs on the detail, not in a row you scan.
- **Chrome that repeats on every screen earns its place once, not everywhere.** The active-role chip is on section roots only: a pushed screen's bar already carries a back control, a title long enough to truncate, and the record's own actions, and the grant is one tap away in the drawer, which has room to name the unit kerja too.

When a value is genuinely worth the line, prefer the shorter of two true phrasings ("Kurang", not "Kiriman kurang" under a label already reading "Kiriman"), and never print a count the neighbouring value already contains.

## Responsive rules

`hooks/use-breakpoint.ts` is the only place layout width is classified: `phone` / `tablet` / `large` at 600 and 905 (Material window size classes). Decide on **width, never orientation** — `height >= width` reads a portrait tablet as a phone. Use `atLeast(bp, 'tablet')`, and keep the breakpoint a string so it is safe in a dependency array.

The `AppShell` sidebar is an overlay drawer, not a fixed rail, so a screen gets the full window width minus 18pt padding either side. A phone in portrait has ~354pt — which is why fixed-width table columns do not fit.

Prefer `minHeight` over `height` on anything wrapping text, so a raised system font size cannot clip it.

## Migration in progress — three overlapping conversions

Two of the three have landed; only the StyleSheet conversion is still mid-flight, so check which state a screen is in before editing it. (A fourth, `view` state machines → `Stack` routes, landed with issue #18; what it settled is under Screen architecture above.)

**1. StyleSheet → gluestack + NativeWind.** `components/ui/*` is vendored gluestack; `components/shell/ui.tsx` holds the shared building blocks styled with NativeWind classes from `tailwind.config.js`. Only `unit-kerja-ruang.tsx` is fully converted (via the shared components); every other section still carries a local `StyleSheet.create` in each of its route files. `cx` is exported from `ui.tsx` for the repeated page chrome but **has no consumer yet** — it is scaffolding for the remaining conversions, not an established pattern.

Colours resolve at build time, so a runtime-computed hex has to fall back to inline styles and drifts off the palette. Pass a `className` the caller picks instead. `constants/theme-erp.ts`, `tailwind.config.js`, and `components/ui/gluestack-ui-provider/config.ts` hold the same palette three times — keep them in step.

**A colour class has to be declared in `tailwind.config.js`, provider variable or not.** The semantic tokens (`card`, `background`, `foreground`, `border`, `muted`, `primary`, `destructive`…) take their *values* from the provider's CSS variables, but Tailwind still has to know the name — they are declared as `rgb(var(--token) / <alpha-value>)`, which keeps the runtime value and the `/70` opacity modifiers both working. An undeclared class does not warn: it compiles to nothing, and the surface renders with **no background at all**. Every dialog and every `DataTable` was see-through for exactly this reason.

The palette is otherwise **opaque throughout**. Tints are pre-composited against white and written as hex rather than left as `rgba(…, 0.1)`, which is a different colour over every surface it lands on. Translucency survives only where it is the effect itself: the drawer overlay, a modal scrim, `DataTable`'s edge fade.

**2. `DataTable` → `RecordList`.** `components/shell/record-list.tsx` is the responsive replacement: one row layout that stacks fields on a phone and ranges them right on a tablet, never scrolling horizontally. **A row does two things: tap opens the record, long-press starts multi-select.** There is no ⋮ menu and no swipe drawer — a row is a summary, and what you can do to a record lives on the record, in the detail's header bar. A per-row menu is a second, dimmer copy of that, on the axis a phone has least of. Selection mode stays because acting on eight records at once is the one thing no detail screen can do; `bulkActions` runs immediately and offers `UndoBar` rather than asking first.

**Done — every section list uses it**, and `DataTable`, `PagingBar`, `SearchBar` and `cx` are deleted rather than left as a second way to draw a list. If a list needs a table again, the reason has to be written down first: fixed columns want 640–880pt and a phone in portrait has ~354.

The list's own chrome is `record-list.tsx` too, not each screen's `StyleSheet`: `ListHeader` (the band above the rows), `ListSearch` (the 52pt field inside it), and `NewRecordRow` ("add one" as the list's first row rather than a toolbar button). A row carries one badge, and `badgeTone` is what makes it a *status* rather than a label — a document's position in its flow is what the eye scans a list of thirty for.

`unit-kerja-ruang.tsx` is the one screen with two lists; the tab switch lives inside `ListHeader` because it selects what the list *is*, not how it is filtered.

**3. Paging buttons → infinite scroll. Done.** The API stays paginated; the UI does not. Every API-backed list (`produk`, `pelanggan`, `supplier`, `pembelian`, `penerimaan-susulan`, `retur-pembelian`) now appends; the three seeded sections have no endpoint to page and simply scroll their store. `produk/index.tsx` is still the reference: `PAGE_SIZE` 20, `onEndReached` guarded by an in-flight flag (it fires repeatedly — the threshold is not a guard), and a failed page halting the loop behind a "Coba lagi" button rather than a spinner that never ends. Nothing saves a scroll offset any more: the list stays mounted under the pushed detail and keeps its own.

**Convention:** convert one screen fully as the reference before rolling out. For the StyleSheet conversion that still means translating each screen from its own values rather than forcing a shared set — the screens genuinely disagree on padding and font sizes, and flattening them silently redesigns things. The lists were the exception and are now deliberately identical: a row that looks different per section is not a design, it is drift.
